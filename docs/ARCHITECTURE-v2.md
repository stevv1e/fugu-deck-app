# Fugu Deck v2: архитектура

*04.10.2026. Проект v2. Готов прототип на одиночном сервере: устройства, DPoP, подписанные подтверждения и мобильное приложение (раздел 3.7). Пояснения «что, зачем и почему» — в `fugu-deck-v2-explained.md`.
Версия v1 (PWA, вход по passkey в control-plane, ключи только на телефоне, удаление через 72 ч) реализована и лежит в репозитории:
`docs/ARCHITECTURE.md`, коммит `eb8d998`.*

## 0. Коротко

### 0.1. Что меняется по сравнению с v1

| | v1 (сделано) | v2 |
|---|---|---|
| Клиент | PWA | **нативное приложение** iOS и Android |
| Кто может обращаться к API | любой с токеном | **только зарегистрированное устройство:** mTLS + токены, привязанные к ключу устройства (DPoP) |
| Вход каждый день | passkey в control-plane | **Face ID / отпечаток + ключ в чипе телефона**; браузер не нужен |
| Keycloak | — | **только первый вход по приглашению и восстановление**; паролей нет, только passkey |
| Подтверждение важных действий | повторный вход | **подпись самого действия ключом телефона с Face ID** (transaction signing) |
| Ключи ИИ и Git | на телефоне, в поде — RAM на 30 мин | **OpenBao**; читает их **только keyguard** и сам подставляет в запросы. В пространства ключи **не попадают** |
| Ввод ключа | — | приложение шифрует ключ **для keyguard**; control-plane передаёт только шифротекст |
| Ключ спонсора в общем чате | пока спонсор в сети + 30 мин | **подписанное спонсором разрешение** на срок; лимиты считает keyguard |
| Агенты | один встроенный | **создаваемые агенты**, в том числе с **SSH к серверам пользователя** через ssh-gateway |
| Память | заметки проекта с поиском | **База знаний**: заметки со связями (как Obsidian), показанные на выбор пользователя мозгом, паутиной или деревом Иггдрасиль — области, свежесть, источники, работа агента в реальном времени; агент берёт заметки вместо исходников |
| Выход в интернет | общий белый список | запросы к ИИ и Git — через keyguard; остальное — белый список на пространство и агента |
| Удаление | сразу | через **space-operator** с задержкой 24 ч, которую можно отменить |
| Бэкапы | — | **непрерывные:** Postgres (WAL), SQLite пространств (Litestream), OpenBao ежечасно |
| Изоляция пространств | контейнер | контейнер **в gVisor** |
| Неактивность | 72 ч | **30 дней** + кнопка «Удалить аккаунт» |
| Админка | в приложении | отдельный realm и адрес, **VPN + mTLS + YubiKey** |

Не меняются: провайдеры (Claude, Sakana), проекты, память, скилы, realtime, модель общего чата (одна модель, спонсор,
обязательный лимит, голосование 24 ч или «свободно для коллег»), сводка расходов, GitOps через Argo CD.

### 0.2. Главные решения по безопасности

1. **Ключи API видит только keyguard.** Ни control-plane, ни пространства, ни Kubernetes Secret их не содержат.
2. **Всё, что расширяет права или тратит чужие деньги, подписывает человек на своём телефоне.** Подписывается сам текст действия,
   и проверяет подпись тот сервис, который действие выполняет. Взломанный посредник не может ни подделать подтверждение, ни подменить его содержимое.
3. **Доступное из интернета почти ничего не может.** control-plane не читает ключи, не удаляет namespace, не подписывает SSH-сертификаты.
4. **Необратимое — с задержкой и бэкапом.** Удаление через 24 ч; OpenBao хранит версии; бэкапы непрерывные.
5. **Долгоживущих секретов нет.** SSH-сертификаты на 10 минут, сертификаты устройств на 30 дней, токены — минуты.

## 3. Приложение

### 3.1. Стек и распространение

- **Рекомендация: React Native** (Expo, dev client) + нативный модуль безопасности на Swift и Kotlin.
  Переиспользуются API-клиент, логика чатов и 10 тем из текущего фронтенда.
  Альтернативы: Kotlin Multiplatform + нативный интерфейс, или отдельно Swift и Kotlin.
- **Распространение.**
  - iOS — TestFlight (нужен Apple Developer Program, проверить оплату картой Казахстана).
  - Android — Google Play (внутреннее тестирование) или APK. Play Integrity не нужен: см. 3.6.
- **Push-уведомления** (APNs, FCM) несут только тип события и идут через push-relay издателя приложения (3.6).

### 3.2. Два аппаратных ключа

Оба создаются при регистрации устройства в Secure Enclave (iOS) / StrongBox или TEE (Android), без экспорта.

| Ключ | Когда используется | Условие использования |
|---|---|---|
| **ключ сессии** | mTLS (сертификат устройства) и DPoP-подпись каждого запроса | приложение разблокировано (Face ID при открытии) |
| **ключ подтверждения** | подпись важных действий (раздел 3.4) | **Face ID или отпечаток на каждую подпись** (iOS `biometryCurrentSet`, Android `setUserAuthenticationRequired` + `BiometricPrompt`) |

Ключ подтверждения становится недействительным, если на телефоне сменили набор отпечатков или лиц. Тогда нужна повторная регистрация устройства.

Если на iOS аппаратный ключ нельзя использовать для TLS напрямую, ключ mTLS хранится в Keychain без экспорта (`ThisDeviceOnly`),
а аппаратный ключ сессии используется для DPoP. Это проверяется прототипом в первую очередь.

### 3.3. Регистрация устройства и ежедневный вход

**Первое устройство (по приглашению):**
```
1. Пригласивший создаёт приглашение → QR-код с одноразовым токеном (24 ч, привязан к нику), передаётся лично или в мессенджере.
2. Приложение сканирует QR (адрес сервера + отпечаток его ключа, 3.6), создаёт два ключа, получает аттестацию (App Attest / Android Key Attestation).
3. Системный браузер → id.<домен>/join?invite=… → Traefik forwardAuth: control-plane проверяет токен приглашения
   и ставит короткую cookie (30 мин); без неё браузерные страницы Keycloak не открываются.
4. Keycloak: регистрация passkey (пароля нет). Возврат в приложение с кодом (PKCE).
5. Обмен кода на токены с DPoP (ключ сессии) → Keycloak выпускает токены, привязанные к ключу сессии.
6. Приложение → keyguard (через control-plane): публичные ключи устройства + аттестация + токен Keycloak.
   keyguard проверяет, что токен выпущен Keycloak для этого ключа сессии (cnf.jkt), и записывает устройство в свой реестр.
7. Пригласивший подтверждает устройство своим ключом подтверждения («Анна зарегистрировала iPhone — подтвердить?»).
8. OpenBao PKI выпускает сертификат устройства на 30 дней. Дальше — только api.<домен> по mTLS.
```

**Второе и следующие устройства:** тот же путь, но с приглашением от самого себя: QR на уже зарегистрированном устройстве,
и подтверждение подписью с него. Если все устройства потеряны — новое приглашение от администратора.

**Каждый день:**
- Face ID открывает приложение (локально).
- Токены обновляются через token endpoint Keycloak **по mTLS и DPoP**, без браузера.
- Сессия Keycloak скользящая, 30 дней. Не заходил 30 дней — refresh-токен истёк, и одновременно срабатывает правило удаления.

**Отзыв устройства.** «Настройки → Устройства» (подпись с другого устройства) или администратор:
- keyguard помечает устройство отозванным;
- control-plane перестаёт принимать его сертификат (проверка серийного номера);
- Keycloak гасит его сессии.

### 3.4. Подпись действий (transaction signing)

**Что подписывается** ключом подтверждения:
- ввод, замена и удаление ключа API;
- разрешение спонсора и его изменение;
- добавление сервера и SSH-доступа агенту;
- подтверждение SSH-команд уровня «запись» и «опасно»;
- смена ролей;
- подтверждение нового устройства;
- удаление аккаунта.

**Формат:** канонический JSON
`{type, поля действия, space, device_id, nonce, ts}` → ECDSA P-256.

**Правило отображения.** Текст, который видит человек, приложение **строит само из полей действия**, а не берёт готовый текст с сервера.
Иначе сервер мог бы показать одно, а дать подписать другое.

**Проверяет тот, кто выполняет действие:** keyguard (ключи, разрешения, устройства, роли) или ssh-gateway (через keyguard).
Проверки:
- подпись верна;
- устройство в реестре и не отозвано;
- `ts` не старше 5 минут;
- `nonce` не использовался.

### 3.5. Ввод ключа API

```
приложение: ключ → HPKE-шифрование на публичный ключ keyguard (из /.well-known, подписан ключом идентичности сервера, 3.6)
            + подпись ключом подтверждения
control-plane: передаёт шифротекст, не может его расшифровать
keyguard: расшифровывает, проверяет подпись и тестовым запросом к провайдеру — рабочий ли ключ,
          пишет в OpenBao, возвращает маску «sk-ant-…a1B2»
```

### 3.6. Свой сервер: адрес указывает пользователь

Приложение не привязано к одному домену: человек подключается к любому серверу Fugu Deck и может держать несколько.

**Как сервер попадает в приложение:**
- **QR-приглашение** владельца: `fugudeck://add?url=…&fp=…&name=…` — адрес и отпечаток ключа сервера.
  Приложение само сверяет отпечаток; не совпал — подключение запрещено.
- **Адрес вручную**: приложение показывает отпечаток (13 групп по 4 символа), человек сверяет его с владельцем
  по другому каналу. Без HTTPS — только адреса локальной сети.

**Идентичность сервера.**
- У сервера ключ Ed25519. `GET /.well-known/fugu-deck` → имя, версия протокола, ключ, способы входа, режим mTLS.
- Отпечаток = base32(SHA-256(ключ)). Приложение считает его само, а не берёт поле ответа.
- Ключ **закрепляется** при добавлении и сверяется при каждом подключении. Сменился — вход блокируется:
  «сверьте новый отпечаток с владельцем и добавьте сервер заново».
- При регистрации оба ключа телефона подписывают `{type: "enroll", challenge, server: отпечаток, session_jkt, confirm_jkt}`.
  Сервер отвечает **квитанцией, подписанной ключом идентичности**. Подставной сервер, даже с настоящим TLS-сертификатом
  на чужой домен, квитанцию не подпишет.
- Всё, что раньше «зашивалось в приложение» (HPKE-ключ keyguard, списки отзыва), сервер отдаёт подписанным ключом идентичности.

**Что меняется, когда серверы чужие для издателя приложения:**

| Было (один домен) | Стало (любой сервер) | Почему |
|---|---|---|
| Play Integrity | Android Key Attestation (Android), App Attest (iOS) | Play Integrity проверяется только через Google API с ключом проекта издателя — у самостоятельного сервера его нет. Key Attestation и App Attest проверяются офлайн по публичным корням Google и Apple. |
| APNs/FCM напрямую с сервера | **push-relay** издателя: сервер шлёт `{токен устройства, тип события}`, relay пересылает | Ключи APNs/FCM принадлежат издателю и серверам не раздаются. Без relay приложение берёт события при открытии. |
| Редирект Keycloak на App/Universal Link | схема `fugudeck://oauth` + PKCE + DPoP | App/Universal Links требуют файла на домене издателя, а домен у каждого сервера свой. PKCE не даёт воспользоваться перехваченным кодом. |
| Сертификат устройства от OpenBao PKI кластера | от CA устройств конкретного сервера | у каждого сервера свой CA и свой реестр устройств |

**mTLS** (`MTLS_MODE`: `off` / `optional` / `required`). Прокси (Caddy, Traefik) проверяет клиентский сертификат
по CA устройств сервера и передаёт серийный номер заголовком `X-Client-Cert-Serial`; сервер сверяет его с реестром.
Сертификат выпускается на **ключ сессии** (CSR подписан в чипе), живёт 30 дней и продлевается с самого устройства.

**Подпись подтверждений.** Телефон сам считает SHA-256 канонического JSON аргументов, которые показывает человеку,
и подписывает `{type: "approve_tool", approval_id, tool, args_sha256, approve, device_id, nonce, ts}`.
Сервер считает тот же хэш по аргументам, которые реально выполнит. Канонический JSON общий для Python и JavaScript
(ключи по кодовым точкам, числа в формате JavaScript), это проверяется тестами байт в байт.

### 3.7. Состояние прототипа (одиночный сервер)

| Часть | Где | Проверено |
|---|---|---|
| идентичность сервера, регистрация, DPoP, подписанные подтверждения, отзыв, CA устройств, mTLS по заголовку | `backend/app/devices.py`, `main.py` | pytest, сквозной тест приложения |
| ядро приложения: протокол, ключи, SSE, подписи, CSR | `mobile/src/core` | юнит-тесты в Node + 13 проверок против живого сервера |
| экраны: серверы, QR/адрес, вход, проекты, чат, подтверждения, устройства, приглашение, темы | `mobile/src/app` | веб-сборка в Playwright |
| нативный модуль: Secure Enclave, StrongBox/TEE, BiometricPrompt, Key Attestation, App Attest, mTLS-транспорт | `mobile/modules/fd-secure` | **не компилировался** — нужна dev-сборка |
| проверка аттестации на сервере, push-relay, вход в кластер через Keycloak | — | следующий этап |

## 4. Keycloak

- **Realm `deck`** (пользователи, `id.<домен>`).
  - Только passkey, паролей и OTP нет.
  - Самостоятельная регистрация выключена.
  - Защита от подбора включена.
  - Клиент `deck-app`: публичный, PKCE, DPoP обязателен, токены привязаны к сертификату (mTLS certificate-bound), redirect только в приложение.
- **Маршруты `id.<домен>`.**
  - TLS принимает сертификат клиента, если он есть.
  - Token endpoint и JWKS открыты. Keycloak сам отклоняет запрос `deck-app` без сертификата устройства и DPoP.
  - Все браузерные страницы — только через forwardAuth «приглашение» (3.3).
- **Realm `ops`** (администраторы): frontend URL — `admin.<домен>`, доступен только из VPN с mTLS.
  Вход в OpenBao, Argo CD и Grafana — через этот realm.
- **Выключено:** token exchange, device flow, самостоятельная регистрация, неиспользуемые IdP. Обновления безопасности ставятся быстро.
- **Admin API** доступен control-plane только для создания и блокировки пользователей. Удаление пользователя делает space-operator при удалении аккаунта.

## 5. keyguard и ключи

### 5.1. Что делает keyguard

1. **Хранит ключи.** Единственный, кто может читать и писать `deck/keys/<user>` в OpenBao.
2. **Прокси к провайдерам.** Пространство шлёт запрос к модели или Git **без ключа**, keyguard проверяет право и подставляет ключ:
   - `POST http://keyguard.deck-keys/llm/anthropic/v1/messages`
   - `POST http://keyguard.deck-keys/llm/sakana/v1/chat/completions`
   - `* http://keyguard.deck-keys/git/github/...`, `.../git/gitlab/...`

   Стриминг проходит насквозь. keyguard сам считает токены по ответу провайдера (usage) и ведёт **авторитетный учёт расходов** для лимитов.
3. **Реестр устройств.** Публичные ключи сессии и подтверждения, аттестация, статус. Регистрация — только по токену Keycloak, привязанному к этому ключу.
4. **Проверяет подписи действий** (3.4) и хранит разрешения спонсоров.
5. **Считает лимиты:** спонсорство, агент, участник. Лимит исчерпан — запрос к провайдеру не уходит.

### 5.2. Как keyguard понимает, чей ключ подставить

- **Кто пришёл.** Пространство предъявляет **проецируемый токен ServiceAccount** с audience `keyguard`: живёт 10 мин, kubelet обновляет его сам.
  По нему keyguard узнаёт namespace. Статических секретов у пространства нет.
- **Личное пространство:** ключ владельца. Дополнительно — лимит агента, если он задан.
- **Общее пространство:** заголовок с id чата → действующее разрешение спонсора на этот чат, провайдер и модель → ключ спонсора, если:
  - срок не истёк;
  - лимиты спонсорства не исчерпаны;
  - не превышен лимит на участника (если задан);
  - запускающий участник в списке допущенных спонсором.
- **Git в общем пространстве:** командный токен владельца или Git-разрешение участника (подписывается так же, как разрешение спонсора).

### 5.3. Разрешение спонсора

Спонсор подписывает на телефоне:
```json
{"type": "grant", "space": "t-shop", "chat": "c-42", "provider": "sakana", "model": "fugu-max-v1.0",
 "limit_usd": 20, "limit_tokens": null, "until": "2026-10-04", "key_until": "2026-10-04",
 "per_member_usd_day": 5, "members": ["anna", "bob"], "proposal": "p-7", "nonce": "…", "ts": …}
```
- **Сроки.** `key_until` — срок доступа к ключу: 24 ч / 7 дней / 30 дней / до конца спонсорства (не дольше `until` и не дольше года).
- **Активация.** Разрешение хранится в keyguard и становится активным, когда пространство сообщает, что модель утверждена
  (сразу, при правиле «свободно» или после голосования). Взломанное пространство может лишь «утвердить» то, на что спонсор уже согласился.
- **Снятие.**
  - Спонсор подписывает отзыв.
  - Без подписи снимать может control-plane или пространство, если модель сменилась, спонсора удалили или предложение отклонено или истекло:
    уменьшение прав подписи не требует.
- **Уведомления спонсору** на 50/80/100 % лимита — push с кнопкой «отозвать».

### 5.4. Права в OpenBao

| Кто | Права |
|---|---|
| keyguard | `deck/keys/*`: чтение и запись; `pki-device/issue/device` — выпуск сертификатов устройств |
| ssh-gateway | `ssh-client-signer/sign/agent` — только подпись SSH-сертификатов |
| ESO | `platform/*` — только чтение служебных секретов |
| control-plane | **нет доступа** |
| пространства | **нет доступа** |
| администраторы (realm `ops`) | управление; root-токен отозван; audit device включён |

- **Удаление.** В KV v2 хранится история версий, но `destroy` и `delete metadata` разрешены только keyguard и только при удалении аккаунта
  (после задержки 24 ч, подписанной или по таймеру 30 дней).
- **Распечатывание.** Вручную, ключами Шамира 3 из 5, с алертом «OpenBao sealed»; позже — внешний KMS.
  Пока OpenBao запечатан, keyguard работает из своего кэша ключей в памяти (15 мин) и не принимает новые ключи.

## 6. Пространства и space-operator

### 6.1. Пространство

- Namespace (PSS restricted), ResourceQuota, PVC, Deployment (**RuntimeClass `gvisor`**), Service, NetworkPolicy, IngressRoute.
- Контейнеры: Fugu Deck и **Litestream** (непрерывная копия SQLite в `s3://…/spaces/<id>/`).
- **Ключей нет.** Проецируемые токены ServiceAccount с audience `keyguard` и `ssh-gateway`. Kubernetes API недоступен.
- **Сон.** Нет активности 60 мин → 0 реплик. Просыпается за 5–10 с (данные на PVC, SQLite при необходимости восстанавливается из Litestream).

### 6.2. space-operator

- control-plane создаёт и меняет только объекты `Space` (CRD `spaces.deck.fugu`) в `deck-system`. Прав на namespace и поды у него нет.
- space-operator (без входа из интернета) создаёт и обновляет всё остальное, усыпляет и будит.
- **Удаление:** `Space.spec.deleteRequestedAt` → push владельцу «пространство будет удалено через 24 ч — отменить» → через 24 ч space-operator удаляет:
  - namespace;
  - копию Litestream в S3;
  - при удалении аккаунта — ещё и ключи в OpenBao (через keyguard) и пользователя в Keycloak.
- **Kyverno:** удалять namespace `deck-u-*` и `deck-t-*` может только ServiceAccount space-operator.

## 7. Агенты и SSH

### 7.1. Агент

У агента есть:
- имя, модель, инструкции, скилы и память проекта;
- набор инструментов (репозитории, SSH, память);
- список серверов и политика команд;
- лимит расходов (считает keyguard);
- дополнительные домены для Squid;
- позже — расписание.

**Подписью владельца** (или редактора в общем пространстве) закрепляются: список серверов агента, уровень «чтение без подтверждения», лимит.
Их проверяют ssh-gateway и keyguard. Поэтому взломанный control-plane или пространство не могут выдать агенту новые права.

### 7.2. Сервер пользователя

- **Добавление.** Хост, порт, пользователь. Отпечаток ключа хоста подтверждается при первом подключении и закрепляется.
  Регистрация сервера подписывается ключом подтверждения.
- **Способ 1 (рекомендуемый): SSH CA в OpenBao.** На сервере:
  - пользователь `deck-agent`, не root, sudo только на нужные команды;
  - `TrustedUserCAKeys` с публичным ключом CA;
  - `AuthorizedPrincipalsFile` с principal `deck-<id агента>`.

  Сертификат на каждую сессию:
  - срок 10 мин;
  - principal агента;
  - `source-address=<исходящий IP кластера>`;
  - только `permit-pty`, без проброса портов, агента и X11.
- **Способ 2 (если CA поставить нельзя):** постоянный ключ в OpenBao, доступный только ssh-gateway;
  в `authorized_keys` — `from="<IP кластера>",no-port-forwarding,no-agent-forwarding,no-X11-forwarding`.
- **Пароли и личные SSH-ключи пользователя не принимаются.**

### 7.3. ssh-gateway

- Единственный с доступом к серверам пользователей: NetworkPolicy `ipBlock /32` на IP и порт зарегистрированных серверов.
- Проверяет:
  - подписанную привязку «агент ↔ сервер»;
  - уровень команды;
  - для «записи» и «опасно» — подпись подтверждения (для опасных при включённом правиле двух людей — две подписи разных людей);
  - лимит команд за сессию.
- Выполнение: exec без интерактивной оболочки, таймаут 5 мин, ограничение вывода, одна команда за раз на сервер.
- Журнал: команда, кто подтвердил, код выхода, вывод — в пространстве и в журнале шлюза (30 дней).
- «Остановить агента» и блокировка пользователя обрывают сессии.
- Исходящий IP фиксированный (одна нода — её IP; несколько — выделенная egress-нода).

### 7.4. Политика команд и подтверждения

| Уровень | Что | Поведение |
|---|---|---|
| чтение | простые команды из списка (`ls`, `cat`, `tail`, `grep`, `df`, `free`, `ps`, `ss`, `systemctl status`, `journalctl`, `docker ps/logs`, `kubectl get/describe`) без `;`, `\|`, `$( )`, перенаправлений и `sudo` | без подтверждения, если это разрешено подписанной настройкой агента |
| запись | всё остальное | подпись с Face ID |
| опасные | `rm -r`, `dd`, `mkfs`, `shutdown`/`reboot`, файрвол, пользователи, `sshd_config`/`authorized_keys`, `curl \| sh`, `sudo su` | ввести имя сервера + подпись; по желанию второй человек или запрет |

**Помощь человеку при подтверждении:**
- **модель-ревьюер** (та же модель и тот же ключ, что у запуска, учитывается в лимите) коротко объясняет, что сделает команда, и отмечает риски
  и расхождения с задачей;
- для команд с пробным режимом (`--dry-run`, `apt -s`, `terraform plan`) сначала пробный прогон, для правок файлов — diff;
- кнопки «подтвердить всё» нет;
- перед серией изменений агент предлагает снимок диска (LVM/ZFS/btrfs или у хостера).

**Граница безопасности — права `deck-agent` на сервере.** Разбор команд — это удобство.

### 7.5. Prompt injection

- Вывод команд и файлы передаются модели как данные с пометкой.
- Ключей и сертификатов нет ни в пространстве, ни в контексте модели.
- Изменения — только по подписи человека.
- Выход — только через keyguard, Squid и ssh-gateway по спискам.

## 8. База знаний

Развитие памяти проекта из v1. Основа — как в Obsidian (заметки в Markdown со ссылками); показывается не облаком точек,
одним из трёх видов на выбор пользователя: **мозг**, **паутина** или дерево **Иггдрасиль** (раздел 8.4).

### 8.1. Данные

| Элемент | Что это | Хранение |
|---|---|---|
| **Заметка** | Markdown: заголовок, текст, теги, ссылки `[[…]]`; область; источник (чат, коммит, команда, файл@SHA, ручной ввод); метка «из внешнего источника» | SQLite пространства, таблица `notes` + FTS5 |
| **Связь** | тип: `часть`, `зависит от`, `решение по`, `противоречит`, `пример`, `ссылка`; сила (0–1) | таблица `links` |
| **Область и группа** | смысловые кластеры: находятся автоматически (Leiden) и могут переименовываться пользователем | таблица `areas` (с родителем), у заметки — `area_id` |
| **Вектор заметки** | для поиска по смыслу | `sqlite-vec` в той же базе |
| **Источник** | репозиторий, сервер, чат, документ | таблица `sources`, у заметки — `source_id` |
| **Привязка к версии** | файл@SHA, конфигурация сервера (хеш), коммит | у заметки; при изменении источника заметка помечается «устарела» |
| **Журнал использования** | какие заметки агент читал в каком запуске | `note_uses`; из него — свежесть и сила связей |

- База знаний — у каждого пространства своя. Чтение базы другого проекта — как и раньше, **только чтение**.
- **Импорт и экспорт** папки Obsidian: заметки с `[[ссылками]]`, тип связи пишется в frontmatter.
- Старая память v1 переходит в заметки без связей и раскладывается по областям при первой индексации.

### 8.2. Как пополняется

- **Вручную:** пользователь пишет или правит заметки, связывает их.
- **Агентом.** После задачи агент предлагает заметки и связи, например: «prod-1: nginx + app, логи в `/var/log/app`, перезапуск через systemd → часть: prod-1».
  - **Очередь предложений:** принять / исправить / отклонить. В настройках проекта можно разрешить автопринятие для заметок из своих данных.
  - **Заметки из чужих данных** (README чужих репозиториев, логи, вывод команд) получают метку «из внешнего источника» и автоматически не принимаются.
- **Индексация** (ночью, дешёвой моделью, пакетно):
  - пересказ изменившихся файлов и конфигураций;
  - поиск связей;
  - перерасчёт областей;
  - пометка устаревших заметок.

### 8.3. Как агент пользуется базой знаний

```
вопрос → поиск по словам (FTS5) + по смыслу (векторы) → 5–10 заметок
       → + соседи по связям на 1–2 шага (сильные связи — первыми)
       → компактный пакет заметок в контекст модели вместо исходных файлов
       → если заметка устарела — агент перечитывает источник и предлагает обновить заметку
```

- Это главная экономия токенов: короткая заметка вместо тысяч токенов кода или логов.
- **Сила связи растёт**, когда агент использует две заметки в одном запуске. Неиспользуемые связи медленно ослабевают.
- **Заметки «из внешнего источника»** передаются модели с пометкой «данные, не инструкции» (как вывод команд, раздел 7.5).

### 8.4. Отображение: три вида на выбор пользователя

Вид выбирает **пользователь** — переключатель вверху экрана базы знаний, выбор запоминается на устройстве.
Данные, поиск, фильтр по областям, карточка заметки и «мысль агента» одни и те же. Отличается только картинка.
Общий макет с переключателем — артефакт «База знаний Fugu Deck». Это макет, его ещё доделываем.

| | **Мозг** | **Паутина** | **Иггдрасиль** |
|---|---|---|---|
| Области | доли: решения — лобная, инфраструктура — теменная, код — затылочная, люди и агенты — височная, операции — мозжечок | секторы | ветви; веточки — группы |
| Проект | узел в височной доле | центр паутины | ствол |
| Заметка | нейрон с дендритами | капля росы на спице | лист; сердцевина — цвет области |
| Давность | тусклые нейроны | витки: у центра свежие, на краю давно не нужные | блёклые листья опадают |
| Связь | аксон, по сильным бежит сигнал | нить поперёк паутины | светящаяся нить между ветвями |
| Устарела | красное мерцающее кольцо | мутная капля, порванная нить | ржавый лист с красным кольцом |
| Источник | в карточке заметки | якорные нити к источникам | корни уходят в «миры»-источники (с рунами) |
| Работа агента | импульсы, волны по извилинам, ЭЭГ по долям | паук идёт по нитям, паутина вибрирует, связанные заметки откликаются | светлячок поднимается от корня по стволу и ветвям |

Общее для всех видов:
- цвет связи — её тип, «противоречит» — пунктир, толщина — сила;
- заметка из внешнего источника — пунктирное золотое кольцо;
- **реализация:** canvas или WebGL в WebView, либо react-native-skia.
  - Тяжёлая статика (извилины мозга, крона и корни дерева, нити паутины) рассчитывается один раз и кэшируется.
  - Раскладку заметок для каждого вида считает пространство.
  - При сотнях заметок: в паутине спица становится группой, в дереве дальние ветви сворачиваются в бутоны, в мозге нейроны группируются в узлы;
- **обновления в реальном времени** — через поток событий пространства.

### 8.5. Ресурсы

- **Многоязычная модель для векторов** (небольшая, на CPU) — в кластере, один экземпляр на всех: ~0,3–0,6 ГБ RAM.
  Тексты не уходят наружу и не стоят денег. Каждое пространство получает к ней доступ своим проецируемым токеном.
- **Индексация** — токены дешёвой модели через keyguard в пределах лимитов владельца. Пакетный режим со скидкой — вместе со слоем экономии токенов (пока отложен).
- **Диск:** векторы и связи — единицы МБ на тысячу заметок.

## 9. Администрирование

- **Доступ.** WireGuard. `admin.<домен>` только из VPN, mTLS с сертификатом администратора из OpenBao PKI (7–30 дней, ключ на YubiKey), внутри — passkey (realm `ops`).
  SSH к ноде и API Kubernetes — только из VPN.
- **Роли разделены:** администратор кластера ≠ администратор OpenBao.
- **Kyverno запрещает** `exec`, `attach`, отладочные контейнеры и изменение подов в `deck-keys`, `deck-secrets`, `deck-ssh` — для всех, кроме процедуры экстренного доступа.
  Экстренный доступ записывается в журнал и оповещает всех администраторов.
- **Изменения чувствительных компонентов** (keyguard, OpenBao, ssh-gateway, Kyverno) — только через git:
  - подписанные коммиты;
  - защита ветки с ревью второго человека;
  - если администратор один — задержка применения 24 ч и уведомление.
- **Журналы** OpenBao, Kubernetes API, keyguard и ssh-gateway → S3 с Object Lock (удалить нельзя, 90 дней; в журналах только хеши id пользователей).

## 10. Жизненный цикл аккаунта

- **30 дней без входа.**
  - Вход — открытие приложения; работа агентов не считается.
  - Уведомления на 23-й и 29-й день.
  - На 30-й день — удаление (ниже). Refresh-токен к этому моменту уже истёк.
- **«Удалить аккаунт»:** подпись ключом подтверждения → задержка 24 ч с возможностью отменить → space-operator:
  1. keyguard: разрешения этого пользователя в общих чатах сняты, ключи удалены со всеми версиями, устройства удалены.
  2. Агенты остановлены, серверы и SSH-доступы удалены.
  3. Личное пространство: namespace и копия Litestream удалены.
  4. Общие пространства:
     - пользователь исключён;
     - владение передано старейшему редактору; нет участников — пространство удаляется;
     - сообщения обезличены (открытый вопрос: или удалять).
  5. control-plane: записи удалены, в журнале только хеш id.
  6. Keycloak: пользователь удалён.
  7. Бэкапы Postgres и OpenBao хранятся 30 дней, поэтому данные уходят и из них.

### 12.2. Сколько нужно

| Пользователей | Пространств (активных) | vCPU | RAM | Диск NVMe |
|---|---|---|---|---|
| 5, минимум | 8 (3–5) | 4 | 8 ГБ | 60 ГБ |
| **5, рекомендуется** | 8 (3–5) | **4** | **16 ГБ** | **100 ГБ** |
| 15 | 22 (6–10) | 6 | 24 ГБ | 150 ГБ |
| 30 | 45 (10–20) | 8 | 32 ГБ или 2 × 16 ГБ | 250 ГБ |
| 50+ | 75+ | 3 ноды × 6–8 | 3 × 24 ГБ | Longhorn; Keycloak ×2, Postgres ×2–3, OpenBao ×3 |

**Расчёт для 5 человек:**
- обычно ~5,3 + 5 × 0,25 ≈ **6,6 ГБ**;
- худший случай ~5,3 + 8 × 0,6 ≈ **10,1 ГБ** → **16 ГБ**.

**Прочее:**
- фиксированный исходящий IP;
- сервер вне ЕС/UK/CH;
- DNS: `api`, `id`, `admin` + CAA;
- S3 вне ЕС: бэкапы, Litestream, журналы с Object Lock;
- Apple Developer Program, Google Play Console;
- шифрование диска ноды (LUKS, ключ вводится при загрузке или через Clevis/Tang).

## 13. Модель угроз

| Угроза | Защита | Остаток |
|---|---|---|
| Сканеры, боты | mTLS на `api`; браузерные страницы Keycloak только по приглашению; админка в VPN | открыты token/JWKS Keycloak — без сертификата и DPoP бесполезны |
| Подбор и фишинг | паролей нет, только passkey; ежедневный вход — Face ID + ключ в чипе | ноль |
| Украденный токен | DPoP + привязка к сертификату; 5 мин | ноль |
| Изменённое приложение, взломанный телефон | аттестация; устройство подтверждает пригласивший или своё устройство; сервер проверяет все правила сам | такое приложение может ровно то, что и сам пользователь |
| Украденный телефон | Face ID на каждую подпись; отзыв устройства; ключей API на телефоне нет | ноль |
| Украденное приглашение | одноразовое, 24 ч, привязано к нику, новое устройство подтверждает пригласивший | ноль без второго фактора — подтверждения |
| Взлом control-plane | не видит ключи (HPKE до keyguard); подписи не подделать; нет прав на namespace и OpenBao; лимиты запросов | отказ в обслуживании, мусор в данных — восстановление из бэкапа |
| Взлом пространства | ключей нет; gVisor; сеть только к keyguard, Squid, ssh-gateway | тратит в пределах лимитов, пока не отключат; читает чаты этого пространства |
| Участник тратит лимит спонсора | лимит на участника, список допущенных, уведомления 50/80/100 %, счёт в keyguard | в пределах того, что спонсор разрешил |
| Заражение базы знаний (вредный текст в заметке) | заметки из чужих данных помечены, не принимаются автоматически, передаются модели как данные | человек может принять плохую заметку — видно источник, можно откатить |
| Prompt injection | подпись человека, ревьюер, пробный прогон, нет секретов у модели, белые списки | человек может подтвердить плохое — ограничено правами `deck-agent` и снимками |
| Украденный SSH-сертификат | 10 мин, `source-address`, без проброса | ноль |
| Подмена сервера (MITM) | закреплённый отпечаток ключа хоста | ноль |
| Подмена образа | cosign + Kyverno, образы по digest, Trivy | — |
| Уязвимость в нашем коде | Semgrep/CodeQL, тесты атак в CI, пентест; gVisor; малые права каждого компонента | не ноль, но ущерб ограничен одним компонентом |
| Администратор кластера | ключи только в keyguard; запрет exec; изменения через git с ревью; журналы с Object Lock | полный контроль над машиной теоретически даёт доступ к памяти — но не в одиночку и не незаметно |
| Хостер (VPS) | LUKS; позже конфиденциальные ВМ (SEV-SNP / TDX) | доступ к памяти работающей машины |
| Потеря данных | WAL Postgres, Litestream, OpenBao ежечасно, версии KV | секунды (Postgres, SQLite), до часа (OpenBao) |
| Удаление по ошибке или атаке | задержка 24 ч с отменой; удалять namespace может только space-operator | — |

## 15. Открытые вопросы

1. Стек приложения: React Native (рекомендация), Kotlin Multiplatform или отдельно Swift и Kotlin?
2. Сообщения удалённого пользователя в общих чатах: обезличивать или удалять?
3. SMTP нужен? (С QR-приглашениями и push можно обойтись без почты.)
4. Распечатывание OpenBao: вручную или внешний KMS?
5. Сколько администраторов? Правило «ревью второго человека» требует двух; с одним — задержка 24 ч.
6. Агентам по расписанию разрешать только «чтение»?
7. OpenBao или HashiCorp Vault — можно решить позже.
8. Слой экономии токенов (кэш промпта, маршрутизация моделей, кэш ответов) — отложен, решаем отдельно.
9. База знаний: автопринятие заметок агента по умолчанию выключено — так и оставить?
10. Какой вид базы знаний показывать по умолчанию: мозг, паутину или Иггдрасиль?
