# Fugu Deck v2 простыми словами: что, зачем и почему

*04.10.2026. Пояснение к `fugu-deck-architecture.md`: там — «как устроено», здесь — «почему так».*

---

## Часть 1. Задача и главная идея

### 1.1. Что строим

Закрытый сервис для небольшой группы (на старте ~5 человек):
- у каждого в телефоне **приложение**, через которое он работает с **ИИ-агентами** (Claude, Sakana Fugu и другие);
- агенты работают с **репозиториями** и — новое в v2 — **администрируют серверы пользователя по SSH**;
- можно работать **вместе**: общие проекты и чаты, один участник может оплачивать модель для всех (спонсор);
- всё работает на **вашем Kubernetes-кластере** (k3s) вне ЕС.

### 1.2. Почему архитектура поменялась целиком

В v1 ключи жили только в телефоне, а сервер получал их на 30 минут. Безопасно, но агенты не могли работать без вас,
а общий чат останавливался, когда спонсор уходил из сети.

В v2 **ключи хранятся на сервере**. Агенты работают ночью и по расписанию, ключ спонсора действует весь выбранный срок,
перезапуски ничего не ломают. Зато сервер становится ценной целью. Поэтому почти всё остальное в v2 —
**слои защиты вокруг ключей и вокруг доступа к вашим серверам**.

### 1.3. Семь принципов

1. **Входить можно только через наше приложение на зарегистрированном телефоне.**
2. **Ключи API видит ровно один внутренний сервис — keyguard.** Ни то, что доступно из интернета, ни пространства, ни Kubernetes их не видят.
3. **Всё, что расширяет права или тратит чужие деньги, подписывает человек на своём телефоне.** Подписывается сам смысл действия, а проверяет подпись тот, кто действие выполняет.
4. **Каждый компонент может минимум.** Взлом одного даёт мало.
5. **Долгоживущих секретов нет** там, где можно без них.
6. **Необратимое — с задержкой и бэкапом.**
7. **Всё записывается** так, что запись нельзя стереть.

## Часть 2. Карта компонентов

| Компонент | Одной фразой |
|---|---|
| Приложение | единственная «дверь»; в телефоне два аппаратных ключа |
| Traefik | «вахтёр»: проверяет сертификаты устройств и приглашения, направляет запросы |
| Keycloak | «паспортный стол»: учётные записи, первый вход, выпуск пропусков (токенов) |

| control-plane | «диспетчер»: пространства, участники, агенты, серверы. Прав на ценное почти нет |
| space-operator | «завхоз»: создаёт, усыпляет и удаляет комнаты-пространства, удаляет только с задержкой |
| **keyguard** | «кассир в сейфовой комнате»: единственный, кто видит ключи; сам подставляет их в запросы и считает деньги |
| OpenBao | «сейф» для ключей, сертификатов, SSH-подписей |
| Пространство | рабочая комната пользователя или команды; ключей внутри нет |
| gVisor | «стена потолще» вокруг каждой комнаты |

| Squid | «таможня» для остального интернета, по спискам |

| Argo CD | кластер = репозиторий (GitOps) |
| База знаний | заметки проекта со связями; вид на выбор — мозг, паутина или Иггдрасиль; агент читает заметки вместо исходников |
| WireGuard | VPN для администратора |

## Часть 3. Каждый компонент подробно

### 3.1. Нативное приложение

**Почему не PWA.** Браузер не даёт того, на чём держится защита:

| Нужно | PWA | Нативное приложение |
|---|---|---|
| Ключ, который нельзя вытащить из телефона | нет прямого доступа | Secure Enclave / StrongBox |
| Ключ, который работает только после Face ID на каждое использование | нет | да |
| Доказать серверу, что это наше неизменённое приложение | нет | App Attest / Android Key Attestation |
| Сертификат клиента (mTLS) | браузер так не умеет | да |
| Надёжные push на iOS | ограниченно | да |

**Почему React Native (рекомендация).** Текущий интерфейс на React и TypeScript переносится почти целиком, одно приложение на обе платформы.
Всё, что касается безопасности, — небольшой нативный модуль на Swift и Kotlin. Его в любом случае пришлось бы писать нативно.

**Что нужно снаружи.**
- Apple Developer Program: TestFlight и App Attest. Проверить оплату картой Казахстана.
- Google Play Console: внутреннее тестирование (или раздача APK). Play Integrity не используется — почему, см. 3.5а.

### 3.2. Два ключа в телефоне

При регистрации устройства в защищённом чипе создаются **два** ключа. Закрытая часть обоих никогда не покидает чип.

- **Ключ сессии** подписывает каждый запрос и служит для сертификата устройства. Работает, пока приложение открыто: Face ID при открытии.
- **Ключ подтверждения** подписывает важные действия и **требует Face ID или отпечаток на каждую подпись**.
  Сменили отпечатки на телефоне — ключ сам становится недействительным.

**Зачем два, а не один.** Ключом сессии подписывается каждый запрос, и спрашивать Face ID на каждый невозможно.
А важные действия должны подтверждаться именно человеком, прямо сейчас. Один ключ — удобство, второй — «подпись в присутствии».

### 3.3. Как работает «вход только из приложения»

1. **Сертификат устройства (mTLS).** Обычный HTTPS доказывает телефону, что сервер настоящий. mTLS — ещё и обратное: телефон предъявляет свой сертификат.
   `api.<домен>` без него обрывает соединение ещё до того, как запрос дойдёт до наших программ. Браузеры, скрипты и сканеры отваливаются на входе.
2. **Токены привязаны к ключу (DPoP).** Каждый запрос подписан ключом сессии, а в токене записан отпечаток этого ключа.
   Украденный токен без чипа бесполезен.
3. **Аттестация.** При регистрации Apple или Google подтверждают, что ключ в чипе и приложение наше.
   На взломанном телефоне её иногда обманывают, поэтому система построена так, что **подлинность приложения не нужна для безопасности**:
   все правила проверяет сервер, и изменённое приложение может ровно то же, что и его владелец.
4. **Регистрация только по приглашению с подтверждением.** Чужак не заведёт своё устройство:
   - нужен одноразовый QR-код приглашения;
   - пригласивший должен подтвердить новое устройство подписью со своего телефона.

**Сертификат живёт 30 дней.** Traefik не проверяет списки отзыва, поэтому сертификат недолгий и продлевается сам.
Отозванное устройство дополнительно блокирует control-plane по серийному номеру.

### 3.4. Первый вход и ежедневный вход

**Первый вход (по приглашению).**
- Пригласивший создаёт приглашение, приложение показывает QR (одноразовый, 24 ч, привязан к нику). Передаётся лично или в мессенджере.
- Новый пользователь сканирует QR → телефон создаёт ключи → открывается системный браузер на странице Keycloak.
- Страницы Keycloak пускают **только** с действующим приглашением: Traefik сначала спрашивает control-plane (forwardAuth).
  Для чужих эта дверь закрыта.
- В Keycloak регистрируется **passkey** (пароля нет вообще). Приложение получает токены, привязанные к ключу сессии, регистрирует устройство
  в keyguard. Пригласивший подтверждает устройство, и приложение получает сертификат.

**Каждый день.** Face ID открывает приложение, токены обновляются в фоне по mTLS и DPoP. Браузер и Keycloak на экране не появляются.

**Почему паролей нет совсем.** Пароль можно подобрать или выманить на поддельной странице. Passkey привязан к домену и на подделке не работает.

**Цена.** Потерял единственный телефон — ждёшь нового приглашения от администратора. Поэтому стоит завести второе устройство или YubiKey.

**Почему сессия 30 дней.** Столько же, сколько правило удаления: не заходил 30 дней — и сессия истекла, и аккаунт удаляется.

### 3.5. Подпись действий

**Что это.** Перед важным действием приложение показывает, что именно будет сделано, человек подтверждает Face ID,
и ключ подтверждения подписывает **содержимое** действия, например:
- «выдать ключ Sakana в чат "Релиз" на 7 дней, лимит $20, участникам Анна и Боб»;
- «выполнить `sudo systemctl restart app` на prod-1»;
- «удалить аккаунт».

**Почему это лучше повторного входа в Keycloak.** Повторный вход доказывает только «человек сейчас здесь». Но что он подтверждал?
Если control-plane взломан, он мог показать «выдать $5», а отправить «выдать $500». Подпись под содержимым такое исключает:
- **текст для человека приложение строит само** из полей действия, а не берёт готовый с сервера;
- **подпись проверяет тот, кто выполняет** (keyguard или ssh-gateway), а не посредник;
- **старую подпись нельзя использовать повторно:** в ней время и одноразовый номер.

Итог: никакой посредник не может ни подделать подтверждение, ни изменить его смысл.

**Что подписывается:**
- ключи API;
- разрешения спонсоров;
- серверы и SSH-доступ агентов, настройки прав агента;
- команды «запись» и «опасно»;
- роли;
- новые устройства;
- удаление аккаунта.

**Что не подписывается:** голосование, чат, чтение. Там нечего подделывать ради выгоды, а подписи на каждое сообщение утомляют.

### 3.5а. Свой сервер: QR или адрес

**Что это.** Приложение одно, а серверов много: у вас свой, у коллег свой. Пользователь сам добавляет сервер —
сканирует QR-приглашение владельца или вводит адрес. Серверов в приложении может быть несколько.

**Как приложение понимает, что сервер тот самый.** У каждого сервера есть свой ключ (Ed25519), а у ключа — отпечаток:
52 символа, которые приложение показывает группами по четыре.
- В **QR** зашиты адрес и отпечаток. Приложение само сверяет их с тем, что ответил сервер. Не совпало — подключиться нельзя.
- При **ручном вводе** приложение показывает отпечаток и просит сверить его с владельцем по другому каналу:
  лично, по телефону, в мессенджере. Совпадает — добавляем.
- Дальше отпечаток **закреплён**. При каждом подключении приложение проверяет, что ключ сервера не изменился.

**Почему одного HTTPS мало.** HTTPS подтверждает домен, но не то, что это ваш сервер: сертификат на похожий домен
получить нетрудно. Поэтому при регистрации телефона сервер подписывает ответ своим ключом.
Подставной сервер этого ключа не имеет и подписать не сможет.

**Что пришлось поменять из-за «чужих» серверов.**
- **Play Integrity → Android Key Attestation.** Ответ Play Integrity проверяется только через Google
  с ключами издателя приложения, а у вашего сервера их нет. Key Attestation проверяется по открытым корням Google,
  без посредников. На iOS по той же причине годится App Attest.
- **Push через посредника.** Ключи для APNs и FCM есть только у издателя приложения. Сервер отправляет посреднику
  (push-relay) «у устройства X новое событие», посредник передаёт его Apple или Google. Содержимого там нет — только тип события.
- **Вход через Keycloak возвращается в приложение по схеме `fugudeck://`**, а не по ссылке на домен издателя.
  Чужое приложение с той же схемой может перехватить код, но без PKCE-секрета, который знает только наше приложение,
  код бесполезен.

**Что уже работает (прототип на одиночном сервере).** Добавление сервера по QR и адресу, сверка и закрепление отпечатка,
регистрация телефона с подписанной квитанцией, вход ключом устройства (DPoP), сертификат устройства для mTLS,
подтверждение действий агента подписью с биометрией, отзыв устройства с другого телефона.
Ядро проверено против настоящего сервера, экраны — в веб-сборке. Нативный модуль для чипа написан,
но ещё не собирался: для этого нужна dev-сборка на Mac (iOS) и с Android SDK.

### 3.6. Traefik

Встроенный в k3s обратный прокси.
- Держит TLS 1.3 и сертификаты.
- Требует сертификат устройства на `api` и сертификат администратора на `admin`.
- Через forwardAuth пускает к страницам Keycloak только с приглашением.
- Ограничивает частоту запросов, добавляет заголовки безопасности, направляет `/s/<id>/` в нужное пространство.

Выбран потому, что уже есть в k3s и настраивается объектами Kubernetes из git.

### 3.7. Keycloak

**Что это.** Сервер учётных записей и входа с открытым кодом (OpenID Connect, OAuth 2.0).

**Зачем, если ежедневный вход через ключ в телефоне.** Кто-то должен:
- надёжно установить «это Анна» при первом входе;
- выпускать токены по стандарту, привязанные к устройству;
- уметь блокировать и гасить сессии.

Самописный вход — самое рискованное место любого сервиса. Keycloak даёт passkey (полная поддержка с 26.4), DPoP (официально с 26.4),
привязку токенов к сертификату, защиту от подбора, Admin API.

**Как настроен.**
- **Realm `deck`** — пользователи. Только passkey, без самостоятельной регистрации.
- **Realm `ops`** — администраторы. Отдельный адрес `admin.<домен>`, доступен только из VPN.
  Зачем отдельный: чтобы вход администраторов никак не пересекался с пользовательским и был недоступен из интернета вовсе.
- **Выключено всё лишнее, особенно token exchange.** В 2026 году в нём нашли уязвимость, из-за которой терялась привязка токена к сертификату.
  Отсюда правило: неиспользуемое — выключаем, обновления безопасности — ставим быстро.

### 3.8. Postgres (CloudNativePG)

**Зачем.** Keycloak нужна нормальная база; control-plane и keyguard тоже переезжают на Postgres. В одном кластере Postgres —
раздельные базы и пользователи, сервисы не видят данных друг друга.

**Почему CNPG.** Оператор сам делает реплики, переключение при сбое и **непрерывный бэкап**: журнал изменений (WAL) постоянно уходит в S3.
Базу можно восстановить **на любую секунду** (PITR), а не «на вчерашнюю ночь».

### 3.9. control-plane

**Что делает.**
- API приложения, участники, приглашения, агенты, серверы, уведомления.
- Создаёт описания пространств (`Space`) для space-operator.

**Чего он НЕ может (главное).**
- **Не видит ключей API.** Приложение шифрует ключ для keyguard (3.11), control-plane передаёт шифротекст. Доступа к OpenBao у него нет вообще.
- **Не может подделать подтверждение** — подписи проверяет не он.
- **Не создаёт и не удаляет namespace** — это делает space-operator.
- **Не может подписать SSH-сертификат.**

**Зачем так урезать.** control-plane — единственная наша программа, до которой можно достучаться из интернета (через mTLS, но всё же).
Значит, это самая вероятная цель. Если её взломают, атакующий получит «диспетчерскую» без ключей от сейфа.
Худшее, что он может, — нарушить работу или намусорить в данных, а это восстанавливается из бэкапа.

### 3.10. space-operator

**Что делает.** Следит за описаниями `Space` и приводит кластер в соответствие: создаёт namespace, диск, правила сети, под; усыпляет и будит;
удаляет.

**Зачем отдельно от control-plane.** Удаление namespace — необратимое действие. Отдали его отдельному сервису без входа из интернета,
и **удаление всегда идёт с задержкой 24 ч**: владелец получает push «пространство будет удалено — отменить».
Kyverno дополнительно запрещает удалять namespace пространств кому-либо, кроме space-operator.

### 3.11. keyguard — центральный элемент v2

**Что это.** Наш сервис во внутренней сети, без входа из интернета, со своей базой. **Единственный, кто может читать ключи API.**

**Что делает.**
1. **Подставляет ключи в запросы.** Пространство отправляет запрос к Claude, Sakana или GitHub **без ключа** на адрес keyguard.
   keyguard проверяет, имеет ли пространство право, добавляет ключ и отправляет запрос провайдеру. Ответ, в том числе потоковый, проходит насквозь.
2. **Считает деньги.** По ответу провайдера он знает, сколько потрачено, и **сам** не пропускает запрос, если лимит исчерпан.
   Взломанное пространство лимит не обойдёт: считает не оно.
3. **Хранит реестр устройств** и **проверяет подписи действий.**
4. **Хранит разрешения спонсоров.**
5. **Принимает новые ключи:** расшифровывает, проверяет подпись владельца и пробным запросом — рабочий ли ключ, пишет в OpenBao.

**Почему это закрывает сразу несколько дыр.**
- В пространстве **нечего украсть**: ключей там нет.
- Ключей **нет в Kubernetes Secret**, и администратор кластера не прочитает их командой `kubectl`.
- Лимиты **нельзя обойти** изнутри пространства.
- Ваша идея «шифровать в приложении и расшифровывать на сервере» здесь **имеет смысл**. Она бесполезна для пароля поверх TLS,
  но полезна для ключа API: шифрование идёт до **конкретного внутреннего сервиса**, и все посредники (Traefik, control-plane) видят только шифротекст.
  Используется стандарт HPKE; публичный ключ keyguard зашит в приложение.

**Как keyguard узнаёт, кто пришёл.** Kubernetes выдаёт каждому поду пространства **проецируемый токен** с пометкой «для keyguard».
Он живёт 10 минут и обновляется автоматически. Постоянных паролей у пространства нет.

**Как решает, чей ключ подставить.**
- Личное пространство — ключ владельца.
- Общее — ключ спонсора, если есть действующее подписанное разрешение на этот чат, этого провайдера и эту модель, срок не вышел,
  лимиты не исчерпаны, а запускающий участник в списке допущенных.

**Почему keyguard — самый охраняемый компонент.**
- Входа из интернета нет.
- Kyverno запрещает заходить в его под (`exec`).
- Менять его можно только через подписанные коммиты с ревью.
- Все его действия пишутся в журнал, который нельзя стереть.

### 3.12. OpenBao

**Что это.** Хранилище секретов, открытое ответвление HashiCorp Vault (появилось после смены лицензии Vault в 2023 году, Linux Foundation).
API совместим с Vault, поэтому переехать потом можно без переписывания.

**Как устроено.**
- Всё зашифровано.
- После запуска сейф нужно **распечатать** частями ключа по схеме Шамира: например 3 из 5, никто в одиночку не откроет.
- Доступ по политикам.
- **Аудит** каждого обращения; значения в журнале хешируются.

**Что внутри и у кого доступ.**
- **Ключи API** — только keyguard.
- **PKI** (центр сертификации) — сертификаты устройств (выпускает keyguard) и администраторов.
- **SSH CA** — только ssh-gateway, только подпись.
- **Служебные пароли платформы** — только ESO.
- control-plane и пространства — **ничего**.

**История версий.** Испорченный ключ можно восстановить из прошлой версии. Стирать историю может только keyguard и только при удалении аккаунта.

**Если OpenBao запечатан** (перезапуск). keyguard 15 минут работает из кэша в памяти, новые ключи не принимает.
Нужен алерт «OpenBao sealed» и человек с частью ключа. Позже — авто-распечатывание через внешний KMS.

### 3.13. Пространство, gVisor и Litestream

**Пространство** — наш сервис с агентами. По одному на пользователя и на команду: отдельный namespace, диск, правила сети.
**Ключей внутри нет.** Засыпает через 60 минут без активности и просыпается за 5–10 секунд.

**gVisor.** Обычный контейнер делит ядро Linux с сервером. Уязвимость в ядре может дать выход «за стену».
gVisor ставит между контейнером и ядром свой слой, который перехватывает системные вызовы. Выйти за пределы гораздо сложнее.
Цена — около 10–20 % процессора на системных вызовах. Агенты в основном ждут ответа модели, поэтому на практике это почти незаметно.

**Litestream.** Каждое пространство хранит данные в SQLite. Litestream рядом с ним постоянно отправляет изменения в S3.
Восстановить можно с точностью до секунд. При удалении аккаунта копия в S3 удаляется вместе с пространством.

### 3.14. Агенты

У каждого агента своё: имя, модель, инструкции, скилы, инструменты, серверы, политика команд, лимит, дополнительные домены.

**Зачем много агентов вместо одного.** Разные задачи — разные права:
- «Ревьюер» только читает репозитории;
- «Дежурный» читает логи двух серверов;
- «Деплойщик» перезапускает сервис с подтверждением.

Чем уже права, тем меньше вреда от ошибки или уговоров.

**Права агента подписываются владельцем**, и ssh-gateway с keyguard проверяют эту подпись.
Взломанный control-plane не может тихо добавить агенту сервер или снять подтверждения.

### 3.15. SSH к вашим серверам и ssh-gateway

**Почему SSH-сертификаты, а не обычный ключ.** Обычный ключ — постоянный секрет: украли — заходят, пока не заметят.
Сертификат выдаётся на одну сессию, и в нём записаны ограничения:
- **10 минут** жизни;
- **principal** — под каким именем можно зайти (только этот агент);
- **`source-address`** — только с IP нашего кластера;
- **только терминал** — без проброса портов и агента, сервер нельзя превратить в туннель.

Пара ключей создаётся на сессию и выбрасывается, так что красть нечего.

**Что вы делаете на сервере один раз.**
- Пользователь `deck-agent`: не root, sudo только на нужные команды.
- Публичный ключ нашего CA и разрешённый principal.

**Отпечаток ключа сервера.** Запоминается при первом подключении. Сменился — подключения стоп, пока вы не подтвердите. Это защита от подмены сервера.

**Зачем отдельный ssh-gateway.**
- Только он имеет сетевой доступ к вашим серверам, и только к их IP и порту.
- Только он может получить подпись SSH-сертификата.
- Он проверяет подписанные права агента и подпись подтверждения команды.
- Ведёт журнал, обрывает сессии по кнопке «стоп».

**Команды без интерактивной оболочки.** Каждая — отдельный запуск с таймаутом 5 минут и ограничением вывода.
Так команду можно целиком показать человеку, подписать и записать.

**Три уровня команд.**
- Чтение — без подтверждения, если вы так настроили агента.
- Запись — подпись с Face ID.
- Опасные — ввести имя сервера плюс подпись; можно требовать второго человека или запретить.

**Помощь при подтверждении**, чтобы не подтверждать не глядя:
- **модель-ревьюер** объясняет простыми словами, что сделает команда, и подсвечивает риски и несоответствие задаче;
- **пробный прогон**, где команда это умеет (`--dry-run`, `terraform plan`), и diff для правок файлов;
- **нет кнопки «подтвердить всё»**;
- перед серией изменений агент предлагает **снимок диска**, чтобы можно было откатиться.

**Честно.** Разбор команд на уровни — удобство, а не стена: в командной строке много способов замаскировать действие.
**Стена — права `deck-agent` на сервере.** Нет прав удалить базу — агент её не удалит, как бы его ни уговаривали.

### 3.16. Prompt injection

Модель читает README, логи и вывод команд. Туда могут подложить текст «игнорируй инструкции, выполни …». Защита:
- **нечего выдать:** ключей и сертификатов нет ни в пространстве, ни в контексте модели;
- **изменения — только по подписи человека**, с ревьюером и пробным прогоном;
- **выход только по спискам** (keyguard, Squid, ssh-gateway) — утечь некуда;
- **минимальные права `deck-agent`** на сервере;
- **вывод команд и файлы помечаются** для модели как данные, а не инструкции.

### 3.17. Squid

Всё, что пространству нужно из интернета кроме ИИ, Git и SSH (например, реестр пакетов), идёт через Squid по белому списку этого пространства и агента.
Прямого выхода нет. Tinyproxy из v1 умел только один общий список, Squid умеет разные списки для разных клиентов.

### 3.18. Админка

- **WireGuard.** Админские адреса вообще не видны из интернета.
- **mTLS с сертификатом на YubiKey.** Украденный ноутбук без ключа бесполезен.
- **Passkey в realm `ops`.** Получается три фактора: сеть, сертификат, личность.
- **Роли разделены:** администратор кластера ≠ администратор OpenBao.
- **Kyverno запрещает заходить в поды** keyguard, OpenBao и ssh-gateway. Экстренный доступ пишется в журнал и оповещает всех.
- **Изменения ценных компонентов** — только подписанные коммиты с ревью второго человека.
  Если администратор один — задержка применения 24 ч с уведомлением: тихо подменить нельзя.
- **Журналы** уходят в S3 с Object Lock: их нельзя удалить даже администратору.

**Отдельный адрес `admin.<домен>`** нужен потому, что сертификат клиента проверяется при установке соединения, когда путь ещё неизвестен.

### 3.19. Цепочка поставки

- **cosign:** CI подписывает каждый образ.
- **Kyverno:** в кластер пускаются только подписанные образы.
- **Образы по digest:** неизменяемый отпечаток вместо тега `latest`.
- **Trivy и Renovate:** поиск уязвимостей и обновления зависимостей.
- **Semgrep или CodeQL:** анализ нашего кода.
- **Тесты атак в CI:** без сертификата, чужой токен, повтор подписи, подмена текста подтверждения, обход политики команд.
- **Пентест** перед запуском.

### 3.20. ESO и Argo CD

- **ESO** теперь нужен только для служебных паролей платформы (базы данных, почта): они лежат в OpenBao и попадают туда, где нужны.
  Ключей пользователей он больше не касается.
- **Argo CD** держит кластер в соответствии с репозиторием: изменения только через коммиты, видно кто и когда, можно откатить.

### 3.21. База знаний

**Что это.** Память проекта, выросшая в базу знаний как в Obsidian: заметки в Markdown со ссылками `[[…]]` друг на друга.
Отличия от Obsidian:
- связи с **типами**: «часть», «зависит от», «решение по», «противоречит», «пример», «ссылка»;
- у каждой заметки есть **источник** (коммит, файл, сервер, чат) и **привязка к версии**: источник изменился — заметка помечается «устарела»;
- базу пополняет **агент** — вы принимаете или правите его предложения;
- видно **свежесть**: какие заметки используются, а какие давно не нужны.

**Зачем.** Две причины.
1. **Агент не изучает проект каждый раз заново.** Вместо 20–40 тысяч токенов кода и логов он читает 5–10 коротких заметок
   и соседние по связям. Это главная экономия токенов, без всякого кэша. В макете на вопросе про 502 — ~2 тысячи токенов вместо ~41 тысячи (условная оценка).
2. **Знание команды не теряется.** Решения, инциденты, runbook — то, что обычно живёт в головах и чатах, — записано, связано и показывает, где устарело.

**Как агент ищет.**
- Находит заметки по словам (FTS5) и по смыслу (векторы — числовые «отпечатки смысла» текста).
- Добавляет соседей по связям на 1–2 шага, сильные связи — первыми.
- Если заметка устарела — перечитывает источник и предлагает обновить заметку.

Связь между двумя заметками **крепнет**, когда агент использует их вместе, и медленно слабеет, если нет. Как тропинка: по ней ходят — она шире.

**Как показывать: три вида на выбор.** Облако точек, как граф Obsidian, на сотнях заметок превращается в клубок, где ничего не найти.
Поэтому нужна понятная форма. Вид выбирает пользователь: **мозг**, **паутина** или дерево **Иггдрасиль**.
Данные одни и те же, отличается только картинка. Общий макет с переключателем — «База знаний Fugu Deck».

| | Мозг | Паутина | Иггдрасиль |
|---|---|---|---|
| области | доли мозга | секторы | ветви |
| заметки | нейроны | капли росы | листья |
| давность | тусклые нейроны | витки: у центра свежие, на краю старые | блёклые листья опадают |
| источники | в карточке | якорные нити | корни-«миры» |
| агент | импульсы, волны по извилинам, ЭЭГ | паук идёт по нитям, паутина вибрирует | светлячок поднимается от корня |
| чем хорош | «живой», хорошо видна активность во времени | сразу видны давность и источник, вибрация показывает поиск по связям | понятно, откуда знание выросло и к какой области относится |

**Безопасность.**
- База знаний — внутри пространства: у каждого проекта своя, чужую можно только читать (если разрешено).
- **Заражение базы знаний.** Кто-то может положить вредный текст в README или лог, агент сделает из него заметку, а потом будет её «слушаться».
  Поэтому заметки из чужих данных:
  - помечаются «из внешнего источника»;
  - не принимаются автоматически;
  - передаются модели как данные, а не как инструкции.
- У каждой заметки видно, откуда она, и её можно откатить.

**Цена.**
- Небольшая модель для векторов в кластере: +0,3–0,6 ГБ памяти, тексты не уходят наружу.
- Ночная индексация дешёвой моделью: немного токенов из лимита владельца.

## Часть 4. Сценарии

### 4.1. Анна регистрируется

```
1. Админ создаёт приглашение → QR на его телефоне → Анна сканирует при встрече (или получает в мессенджере).
2. Приложение Анны создаёт два ключа в Secure Enclave и получает аттестацию.
3. Браузер → страница Keycloak (открывается, потому что есть приглашение) → Анна регистрирует passkey.
4. Приложение получает токены, привязанные к ключу сессии, и регистрирует устройство в keyguard.
5. Админ получает push «Анна регистрирует iPhone» → Face ID → подпись.
6. Анна получает сертификат устройства; space-operator создаёт её пространство.
```

### 4.2. Анна вводит ключ Claude

```
1. Вставляет ключ → приложение шифрует его для keyguard и подписывает (Face ID).
2. control-plane передаёт шифротекст, прочитать его не может.
3. keyguard расшифровывает, проверяет подпись, делает пробный запрос к Anthropic, пишет ключ в OpenBao, возвращает маску «sk-ant-…a1B2».
4. С этого момента ключ видит только keyguard.
```

### 4.3. Анна просит агента сделать ревью PR

```
агент в пространстве → запрос к Claude без ключа → keyguard: «это пространство Анны, лимит не исчерпан»
→ подставляет ключ → Anthropic → ответ потоком обратно → keyguard записывает расход
```

### 4.4. Боб спонсирует Sakana в общем чате на 7 дней

```
1. Боб предлагает Fugu Max: $20, срок ключа 7 дней, не больше $5 в день на участника, участники Анна и Боб
   → приложение показывает это своими словами → Face ID → подпись.
2. Подписанное разрешение уходит в keyguard и ждёт; в чате идёт голосование (большинство, 24 ч).
3. Анна голосует «за» → пространство сообщает keyguard «утверждено» → разрешение активно.
4. Боб в отпуске — чат работает. keyguard следит за $20, за $5 в день и за сроком; на 80 % Бобу приходит push с кнопкой «отозвать».
5. Через 7 дней keyguard перестаёт подставлять ключ Боба.
```

### 4.5. Агент перезапускает сервис на сервере Вики

```
1. Вика добавила prod-1 (подпись), настроила deck-agent с sudo только на «systemctl restart app», подтвердила отпечаток сервера.
   Права агента «Дежурный»: prod-1, чтение без подтверждения — тоже подписаны Викой.
2. Агент: journalctl -u app -n 200 → ssh-gateway проверяет подписанные права → сертификат на 10 мин → вывод.
3. Агент предлагает «sudo systemctl restart app» → ревьюер: «перезапустит сервис app, будет простой ~5 с»
   → Вика: Face ID → подпись → ssh-gateway проверяет подпись → выполняет.
4. Через 10 минут сертификат сам перестаёт работать.
```

### 4.6. У Анны украли телефон

- Без её лица или отпечатка ключи в чипе не работают.
- С другого устройства (или через админа) Анна отзывает украденное: keyguard, control-plane и Keycloak перестают его принимать.
- Ключей API на телефоне нет.

### 4.7. Взломали control-plane

Что атакующий **не может**:
- читать ключи;
- выдать ключ спонсора;
- дать агенту новый сервер;
- подтвердить команду;
- удалить пространство без 24-часовой задержки с уведомлением владельцу.

Что **может**: нарушить работу и испортить данные в базе control-plane. Лечится восстановлением Postgres на секунду до взлома.

### 4.8. Агент отвечает по базе знаний

```
Вика: «Почему на checkout снова 502?» → агент «Дежурный»:
1. Поиск по базе знаний: заметка «Инцидент 12.09: 502 на checkout» — похожий случай.
2. Соседняя заметка «nginx на prod-1» устарела (конфиг изменился) → агент перечитывает файл на сервере.
3. Логи и заметка «Модуль оплаты»: 3 ретрая по 10 с — дольше таймаута nginx 30 с.
4. Ответ с предложением фикса и вопросом: «Обновить заметку о nginx?»
На экране мозга: импульсы бегут из мозжечка (операции) в теменную долю (nginx, prod-1) и в затылочную (код), на ЭЭГ всплески.
На экране паутины: паук идёт по нитям от «Инцидента» к «nginx» (рядом порванная нить), потом к «Модулю оплаты»; паутина вибрирует.
На экране Иггдрасиля: светлячок поднимается от корня «Чаты» по стволу, через ветвь «Операции» и по нити к листу «nginx».
Связи между использованными заметками крепнут, заметки снова «свежие».
```

### 4.9. Вика удаляет аккаунт

```
Face ID → подпись → «через 24 ч аккаунт будет удалён — отменить» → space-operator:
разрешения в общих чатах сняты · ключи и устройства удалены · агенты и SSH-доступы удалены · пространство и копия Litestream удалены
· из общих пространств исключена, сообщения обезличены · записи в control-plane удалены · пользователь в Keycloak удалён
```
Бэкапы хранятся 30 дней, поэтому данные уходят и из них.

## Часть 5. Модель угроз

| Угроза | Что останавливает | Что остаётся |
|---|---|---|
| Сканеры и боты | mTLS на `api`; страницы Keycloak только по приглашению; админка за VPN | открыты token/JWKS Keycloak — без сертификата и DPoP бесполезны |
| Подбор и фишинг | паролей нет; passkey; ежедневно Face ID + чип | ноль |
| Украденный токен | DPoP + привязка к сертификату | ноль |
| Изменённое приложение | правила проверяет сервер; регистрация по приглашению с подтверждением; аттестация | может то же, что и его владелец |
| Украденный телефон | Face ID на каждую подпись; отзыв; ключей API нет | ноль |
| Украденное приглашение | одноразовое, 24 ч, по нику, новое устройство подтверждает пригласивший | ноль без подтверждения пригласившего |
| Взлом control-plane | HPKE до keyguard; подписи проверяют исполнители; нет прав на OpenBao и namespace | отказ в обслуживании и мусор → восстановление |
| Взлом пространства | ключей нет; gVisor; сеть только к keyguard, Squid, ssh-gateway | тратит в пределах лимитов, пока не отключат; видит чаты этого пространства |
| Участник тратит лимит спонсора | лимит на участника, список допущенных, push на 50/80/100 %, счёт в keyguard | ровно то, что спонсор разрешил |
| Заражение базы знаний | заметки из чужих данных помечены, не принимаются сами, идут модели как данные | человек может принять плохую заметку — видно источник, можно откатить |
| Prompt injection | подпись человека, ревьюер, пробный прогон, нет секретов, белые списки | человек может подтвердить плохое — ограничено правами `deck-agent` и снимком |
| Украденный SSH-сертификат | 10 мин, `source-address`, без проброса | ноль |
| Подмена сервера | закреплённый отпечаток | ноль |
| Подмена образа | cosign + Kyverno, digest | — |
| Уязвимость в нашем коде | анализ кода, тесты атак, пентест, gVisor, малые права | не ноль, но ущерб ограничен одним компонентом |
| Администратор кластера | ключи только в keyguard; запрет exec; изменения через git с ревью или задержкой; журналы нельзя стереть | полный контроль над машиной теоретически даёт доступ к памяти — но не в одиночку и не незаметно |
| Хостер (VPS) | шифрование диска (LUKS); позже конфиденциальные ВМ | доступ к памяти работающей машины |
| Потеря данных | WAL Postgres, Litestream, OpenBao ежечасно, версии ключей | секунды, OpenBao — до часа |
| Удаление по ошибке или атаке | задержка 24 ч с отменой; удалять может только space-operator | — |

### Что нельзя убрать никакой архитектурой

Если сервер пользуется ключом, то тот, кто **полностью** контролирует машину (администратор с физическим доступом или хостер),
теоретически может достать ключ из памяти. Лучшее достижимое:
- **не в одиночку:** роли разделены, ревью второго человека;
- **не незаметно:** журналы, которые нельзя стереть;
- **с ограниченным ущербом:** отдельные ключи с лимитом у провайдера.

Полный ноль был только в v1, где ключи жили в телефоне. От этого вы отказались ради агентов, работающих без вас.

## Часть 6. Цена

**Компоненты.** ~15 вместо ~5 в v1. Регулярная работа:
- распечатать OpenBao после перезапуска;
- обновлять Keycloak;
- следить за бэкапами и алертами;
- продлевать членство Apple;
- ревьюить изменения ценных компонентов.

**Ресурсы на 5 человек.** 4 vCPU, 16 ГБ RAM, 100 ГБ NVMe.
- Система ≈ 4,0–6,7 ГБ (вместе с моделью векторов для базы знаний).
- Пространство с gVisor и Litestream ≈ 0,2–0,3 ГБ, пока активно.
- Плюс S3 вне ЕС и фиксированный исходящий IP.

**Разработка.** Самое сложное — нативный модуль (два ключа, аттестация, mTLS, DPoP, подпись действий) и keyguard. С них и начинаем.

**Если захочется упростить** (по убыванию безопасности, которую теряем):

| Упрощение | Что теряем |
|---|---|
| без Kyverno на старте, добавить в первый месяц | защиту от подменённых образов на это время |
| без аттестации | защиту от поддельного клиента; остаются приглашения, mTLS и DPoP |
| без gVisor | «толстую стену» — выход из контейнера через уязвимость ядра проще |
| без keyguard: ключи через ESO в пространства | **главную защиту v2** — не рекомендую |

## Часть 7. Словарь

| Термин | Что это |
|---|---|
| **TLS / HTTPS** | шифрование соединения; сервер доказывает, что он настоящий |
| **mTLS** | взаимный TLS: клиент тоже предъявляет сертификат |
| **Сертификат / CA** | открытый ключ + подпись центра сертификации / тот, кто подписывает |
| **OIDC / OAuth 2.0** | стандарты входа и выдачи токенов |
| **PKCE** | защита входа в приложениях: перехваченный код бесполезен без секрета приложения |
| **Access / refresh token** | короткий пропуск для запросов / долгий для получения новых коротких |
| **DPoP** | привязка токена к ключу устройства: каждый запрос подписан |
| **Passkey** | вход ключом в устройстве с Face ID или отпечатком; защищён от фишинга |
| **Аттестация** | подписанное Apple/Google подтверждение: «ключ в чипе, приложение настоящее» |
| **Secure Enclave / StrongBox / TEE** | защищённые области телефона, откуда нельзя извлечь ключ |
| **Подпись действия (transaction signing)** | подпись самого содержимого действия ключом с Face ID; проверяет исполнитель |
| **HPKE** | стандарт шифрования «для получателя с открытым ключом»; расшифровать может только он |
| **forwardAuth** | Traefik перед пропуском запроса спрашивает наш сервис «пускать?» |
| **Namespace** | «комната» в Kubernetes со своими объектами и правилами |
| **Оператор / CRD** | программа в кластере, которая приводит систему к описанию / свой тип описаний (`Space`) |
| **Проецируемый токен ServiceAccount** | короткий токен, который Kubernetes сам выдаёт поду для конкретного получателя |
| **NetworkPolicy** | правила, кто с кем может соединяться |
| **gVisor** | дополнительный слой между контейнером и ядром Linux |
| **WAL / PITR** | журнал изменений Postgres / восстановление на любой момент времени |
| **Litestream** | непрерывная копия SQLite в S3 |
| **Object Lock** | режим S3, в котором объект нельзя удалить или изменить до срока |
| **Unseal / схема Шамира** | распечатывание хранилища / ключ делится на N частей, нужно любые K |
| **SSH-сертификат / principal** | SSH-ключ с подписью CA и ограничениями / имя, под которым можно зайти |
| **Prompt injection** | попытка управлять ИИ через текст в данных |
| **Egress** | исходящий трафик |
| **GitOps** | инфраструктура описана в git |
| **Digest / cosign** | неизменяемый отпечаток образа / инструмент подписи образов |
| **LUKS** | шифрование диска в Linux |
| **Вектор (эмбеддинг)** | числовой «отпечаток смысла» текста; близкие по смыслу тексты — близкие векторы |
| **FTS5 / sqlite-vec** | поиск по словам / по векторам внутри SQLite |
| **Leiden** | алгоритм, который находит группы тесно связанных заметок (области и группы) |
