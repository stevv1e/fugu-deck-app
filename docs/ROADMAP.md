# План развития Fugu Deck

Roadmap не привязан к искусственным датам. Приоритет определяется пользовательским риском, безопасностью и проверяемым результатом. Версии ниже — ориентиры объёма, а не обещание сроков.

## 1. Текущая база

### Приложение 0.10.0 — модульная платформа

Реализовано:

- конструктор модулей с шаблонами, локальной отладкой и атомарной GitHub-публикацией;
- Ed25519-подпись официального каталога и отдельные пользовательские Git-источники;
- журнал безопасности агента и модулей;
- экспорт/импорт и ручная E2EE-синхронизация модулей;
- optimistic conflict detection для server sync envelope.

### Приложение 0.11.0 / сервер 0.11.x — Windows pairing

Реализовано:

- 8-символьный код на ПК и подтверждение на телефоне;
- pairing без Bluetooth/USB;
- подписанный `pair_approve`, привязанный к ПК и его ключам;
- OAuth PKCE/DPoP после approved;
- обязательное отдельное `device_approve` после регистрации;
- общие Android/Windows пространства, чаты и модели;
- прямые релизные APK/EXE и обновлённый лендинг.

### Приложение 0.14.1 / сервер 0.12.x — большие видео

- медиа-загрузки до 2 ГБ на Android, Windows и сервере;
- извлечение звуковой дорожки в выделенном FFmpeg-воркере через keyguard;
- потоковая передача без загрузки исходного видео в память и без отправки видео провайдеру транскрибации.

### Приложение 0.14.0 — быстрый переход между пространствами

- переключатель доступен из рабочей области Windows, включая свёрнутую sidebar, и из Android «Ещё»;
- список объединяет standalone-серверы, личные и общие пространства кластеров;
- последний чат, проект, Workspace или вкладка настроек сохраняются отдельно для каждого пространства;
- запуск восстанавливает только проверенный внутренний маршрут выбранного `sid`;
- внешние URL, чужие пространства, login и неизвестные query-параметры не принимаются в `next`.

### Приложение 0.13.0 — выбор пространства

- выбор сервера открывает список личного и общих пространств без автоматического запуска;
- явный выбор запускает или пробуждает только выбранное пространство;
- создание общего пространства доступно на том же экране и не перенаправляет пользователя;
- участники и настройки общего пространства сохранены отдельной кнопкой;
- прямые `/launch/[sid]` и старые deep links продолжают работать.

### Приложение 0.12.0 — минималистичная маршрутизация

- отдельное главное меню для подключений, авторизации и регистрации;
- экран запуска пространства с реальными этапами, повтором и возвратом без выхода;
- разделы чатов, проектов, моделей, серверов, доступов, разрешений и параметров;
- текстовая collapsible-sidebar Windows и компактные вкладки Android;
- Workspace, задачи, интеграции и модули сохранены как явные маршруты;
- центральная колонка desktop-чата и тонкие полосы прокрутки;
- [документация интерфейса](INTERFACE.md) и реестр сохранённых функций.

### Приложение 0.12.1 — исправление запуска

- устранён повторный запуск эффекта `/launch/[sid]` при пересоздании производной записи кластера;
- запуск привязан к стабильному ID устройства, а не к объекту записи;
- отложенный переход отменяется при уходе с экрана;
- общие пространства сохраняют те же проекты, чаты, модели и разрешения; их отдельный маршрут открытия не изменён.

### Ранее завершённые направления

- 44 модели, роли и fallback;
- multi-model `code-review-summary`;
- Workspace, diff, CI, фоновые задачи и SSH Gateway;
- Media Core, большие загрузки, транскрибация, TXT/JSON/SRT и отчёты;
- генерация изображений;
- Google Drive OAuth, чтение, загрузка и создание папок;
- настройки прав агентов и подтверждения опасных операций.

## 2. P0 — стабилизация текущего релиза

Цель: не наращивать функциональность поверх непроверенных сценариев.

### 2.1. Device-to-device acceptance matrix

Проверить на реальных Android и Windows:

- pairing положительный путь, неверный/истёкший код, повтор и отмена;
- повторный запуск Windows и DPoP refresh без браузера;
- revoke ПК и восстановление новым pairing;
- общие чаты, streaming, остановка и multi-model;
- Drive read/write/create folder;
- media >250 МБ, отмена и восстановление частей;
- официальный/custom module, сетевые блокировки и журнал;
- E2EE в обе стороны, неверная фраза и конфликт версий.

Критерий: все пункты имеют фактический результат и известные ограничения занесены в issue/docs.

### 2.2. CI и публикация

- Все необходимые image matrix jobs успешно публикуют и подписывают образы.
- Устранить package Actions access/permission проблемы без широкого PAT в CI.
- Стабилизировать mobile↔keyguard integration job.
- Разобрать старые lint errors отдельно от функциональных изменений.

Критерий: повторный релиз не требует ручных обходов и исключений из проверок.

## 3. P1 — Windows distribution и повторный вход

### 3.1. Подпись и автообновление Windows

- Подпись NSIS установщика доверенным сертификатом издателя.
- Проверка подписи и SHA-256 перед установкой обновления.
- Stable/beta channels и защищённый update manifest.
- Атомарное обновление с откатом на предыдущую рабочую версию.
- Сохранение device keys и пространств при update/rollback.

Критерий: чистая установка, обновление и откат проверены на реальной Windows; revoked device не восстанавливает доступ после update.

### 3.2. Windows Hello после pairing

- После успешной активации предложить создать локальный passkey Windows Hello.
- Оставить pairing код как независимый recovery/fallback.
- Не удалять телефонный passkey при добавлении Windows-ключа.
- Ясно показать, где хранится каждый ключ и как его отозвать.

Критерий: повторный вход по PIN/биометрии работает без телефона; при удалении локального passkey pairing снова работает.

## 4. P1 — автономность и синхронизация

### 4.1. Автоматическая E2EE-синхронизация

- Очередь изменений и фоновая синхронизация модулей.
- Версии/vector clock или эквивалентное обнаружение конфликтов.
- UI конфликта без молчаливого last-write-wins.
- Восстановление после смены парольной фразы и потери конверта.
- Минимизация метаданных на сервере.

Критерий: offline изменения на двух устройствах сходятся без потери; сервер видит только зашифрованный конверт и минимально необходимые метаданные.

### 4.2. Осознанное расширение backup

Отдельно решить, какие локальные настройки и данные standalone действительно нужны пользователю. Не расширять backup автоматически на все AsyncStorage, device keys или provider credentials.

## 5. P2 — второй этап Git-модулей

### 5.1. Безопасные обновления

- Diff манифеста и кода перед обновлением.
- Повторное согласование новых разрешений.
- Rollback на предыдущий pinned commit.
- Проверка совместимости с приложением.

Критерий: усиление разрешений невозможно без явного действия пользователя.

### 5.2. Git/SSH capability

- Отдельные RPC с узкой схемой, без передачи постоянных credentials модулю.
- Подтверждение write/danger через существующий action protocol.
- Лимиты времени, ответа, частоты и полный журнал.

Критерий: модуль без секрета не может обратиться к произвольному Git/SSH или выйти за allowlist.

### 5.3. Server-side sandbox

- Изолированная execution environment без нативных библиотек и произвольного Node.js по умолчанию.
- Отдельные CPU/memory/time/output quotas.
- NetworkPolicy и отсутствие доступа к keyguard secrets.
- Аттестация/подпись выпускаемых модулей и аудит запусков.

Критерий: attack tests доказывают отсутствие побега в backend/control plane/keyguard и произвольного egress.

### 5.4. Настоящий scheduler

Фоновые задания модулей реализуются только после sandbox resource limits и восстановления после перезапуска. Таймер открытой панели не выдаётся за scheduler.

## 6. P2 — расширение media harness

- Диаризация/разметка говорящих при поддержке провайдера.
- Сравнение transcript с исходными таймингами и ручное редактирование.
- Шаблоны отчётов и повторяемые pipelines.
- Drive shared drives/разрешения после отдельного исследования OAuth.
- Очередь нескольких media jobs и контроль расхода.

Критерий каждого пункта: реальные длинные файлы, отмена, стоимость, корректный результат и отсутствие потерянных фрагментов.

## 7. P3 — экосистема и качество

- Больше официальных модулей с понятными примерами безопасности.
- Категории/поиск и совместимость версий в каталоге.
- Публичная документация provider/module development с reference tests.
- Улучшение accessibility, клавиатуры и локализации.
- Наблюдаемость без утечки содержимого чатов/секретов.

## 8. Что сознательно не входит в ближайший план

- Локальные AI-модели на устройствах.
- Произвольный нативный код Git-модулей.
- Отключение device approval, DPoP, mTLS или подписи danger ради удобства.
- Экспорт/синхронизация API/GitHub-ключей в обычном backup.
- Единая кнопка «разрешить всё» вместо гранулированных правил агента.

## 9. Порядок принятия следующих этапов

1. Завершить P0 и заполнить реальную acceptance matrix.
2. Выпустить Windows signing/auto-update и Windows Hello после pairing.
3. Перейти к автоматической E2EE-синхронизации.
4. Только затем расширять module capabilities и server execution.

Каждый этап должен иметь отдельный security review, тесты атак, обновлённую документацию и реальный сценарий на опубликованном артефакте.
