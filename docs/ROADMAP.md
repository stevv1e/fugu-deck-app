# План развития Fugu Deck

Roadmap не привязан к искусственным датам. Приоритет определяется пользовательским риском, безопасностью и проверяемым результатом. Версии ниже — ориентиры объёма, а не обещание сроков.

## 1. Текущая база

### Приложение 0.10.0 — модульная платформа

Реализовано:

- конструктор модулей с шаблонами, локальной отладкой и атомарной GitHub-публикацией;
- Ed25519-подпись официального каталога и отдельные пользовательские Git-источники;
- журнал безопасности агента и модулей;
- экспорт/импорт и ручная E2EE-синхронизация модулей;
- optimistic conflict detection для server sync envelope.

### Приложение 0.11.0 / сервер 0.11.x — Windows pairing

Реализовано:

- 8-символьный код на ПК и подтверждение на телефоне;
- pairing без Bluetooth/USB;
- подписанный `pair_approve`, привязанный к ПК и его ключам;
- OAuth PKCE/DPoP после approved;
- обязательное отдельное `device_approve` после регистрации;
- общие Android/Windows пространства, чаты и модели;
- прямые релизные APK/EXE и обновлённый лендинг.

### Приложение 0.18.1 / Space 0.19.0 / Control Plane 0.12.0 — режимы чата и каналы обновлений

- корневой чат переключается между «Инжинирингом» и «Общением» с сохранением истории, вложений и исходного проекта;
- stable/beta используют отдельные подписанные manifest, beta публикуется из GitHub pre-release;
- Windows получил явный проверенный rollback на предыдущий stable; обычный update не разрешает downgrade;
- Android downgrade поверх не реализован из-за ограничения ОС на меньший `versionCode`;
- Authenticode, автоматический rollback и проверка на реальных устройствах остаются в приёмке.

### Приложение 0.17.1 — Windows Hello после pairing

- после успешного pairing предлагается локальный passkey через Keycloak AIA;
- регистрация необязательна, телефонный passkey не удаляется;
- pairing по коду остаётся recovery, мобильный flow не изменён.

### Space 0.18.0 / Keyguard 0.13.0 — PDF/OCR worker

- PDF до 200 МБ/400 страниц через выделенный worker в Малайзии;
- текст по страницам, OCR только без текстового слоя, таблицы и метаданные изображений;
- DB-backed job, прогресс/отмена, Markdown/JSON как вложения чата;
- потоковый keyguard proxy без произвольного egress и без исполнения активного PDF.

### Приложение и Space 0.17.0 — проверяемая база знаний

- FTS5/BM25, связи и SHA-256 source checks используются без дополнительного embeddings-сервиса;
- источник, ревизия, last_checked/last_verified, valid_from и verification_error видны агенту и в UI;
- недоступный источник явно отличается от fresh и stale; ручная пометка stale сохраняется.

### Space 0.16.2 — Context/Budget Harness

- лимиты времени, суммарных токенов, стоимости и tool calls в дополнение к шагам;
- суммарный usage виден в событиях запуска, cached tokens учитываются отдельно;
- последовательные read-only вызовы выполняются параллельно без изменения порядка сохранения результатов;
- существующие stable prefix caching, compaction и ограничение старых tool results сохранены.

### Приложение 0.16.1 — подписанные обновления

- Ed25519 update-манифесты для Android/Windows, точные Release URL, размер и SHA-256;
- фоновая загрузка с прогрессом, отмена Android и системный установщик;
- Windows запускает только проверенный installer handle и позволяет отложить перезапуск;
- beta-канал и явный Windows rollback добавлены в 0.18.1; Authenticode и автоматический rollback остаются отдельным этапом.

### Приложение и Space 0.15.1 — файлы Windows

- нативные file/photo picker, drag-and-drop, несколько файлов и Unicode-имена;
- файловый bridge выдаёт renderer случайные handles только для выбранных/перетащенных файлов;
- chunked upload с прогрессом, отменой и повтором с принятого сервером offset;
- нативные открытие и сохранение вложений Windows;
- контроль `mtimeNs`/`ctimeNs`, размера и границ каждой части.

### Приложение 0.14.1 / сервер 0.12.x — большие видео

- медиа-загрузки до 2 ГБ на Android, Windows и сервере;
- извлечение звуковой дорожки в выделенном FFmpeg-воркере через keyguard;
- потоковая передача без загрузки исходного видео в память и без отправки видео провайдеру транскрибации.

### Приложение 0.14.0 — быстрый переход между пространствами

- переключатель доступен из рабочей области Windows, включая свёрнутую sidebar, и из Android «Ещё»;
- список объединяет standalone-серверы, личные и общие пространства кластеров;
- последний чат, проект, Workspace или вкладка настроек сохраняются отдельно для каждого пространства;
- запуск восстанавливает только проверенный внутренний маршрут выбранного `sid`;
- внешние URL, чужие пространства, login и неизвестные query-параметры не принимаются в `next`.

### Приложение 0.13.0 — выбор пространства

- выбор сервера открывает список личного и общих пространств без автоматического запуска;
- явный выбор запускает или пробуждает только выбранное пространство;
- создание общего пространства доступно на том же экране и не перенаправляет пользователя;
- участники и настройки общего пространства сохранены отдельной кнопкой;
- прямые `/launch/[sid]` и старые deep links продолжают работать.

### Приложение 0.12.0 — минималистичная маршрутизация

- отдельное главное меню для подключений, авторизации и регистрации;
- экран запуска пространства с реальными этапами, повтором и возвратом без выхода;
- разделы чатов, проектов, моделей, серверов, доступов, разрешений и параметров;
- текстовая collapsible-sidebar Windows и компактные вкладки Android;
- Workspace, задачи, интеграции и модули сохранены как явные маршруты;
- центральная колонка desktop-чата и тонкие полосы прокрутки;
- [документация интерфейса](INTERFACE.md) и реестр сохранённых функций.

### Приложение 0.12.1 — исправление запуска

- устранён повторный запуск эффекта `/launch/[sid]` при пересоздании производной записи кластера;
- запуск привязан к стабильному ID устройства, а не к объекту записи;
- отложенный переход отменяется при уходе с экрана;
- общие пространства сохраняют те же проекты, чаты, модели и разрешения; их отдельный маршрут открытия не изменён.

### Ранее завершённые направления

- 44 модели, роли и fallback;
- multi-model `code-review-summary`;
- Workspace, diff, CI, фоновые задачи и SSH Gateway;
- Media Core, большие загрузки, транскрибация, TXT/JSON/SRT и отчёты;
- генерация изображений;
- Google Drive OAuth, чтение, загрузка и создание папок;
- настройки прав агентов и подтверждения опасных операций.

## 2. P0 — стабилизация текущего релиза

Цель: не наращивать функциональность поверх непроверенных сценариев.

### 2.1. Device-to-device acceptance matrix

Текущие результаты и незакрытые ручные сценарии: [ACCEPTANCE.md](ACCEPTANCE.md).

Проверить на реальных Android и Windows:

- pairing положительный путь, неверный/истёкший код, повтор и отмена;
- повторный запуск Windows и DPoP refresh без браузера;
- revoke ПК и восстановление новым pairing;
- общие чаты, streaming, остановка и multi-model;
- Drive read/write/create folder;
- media >250 МБ, отмена и восстановление частей;
- официальный/custom module, сетевые блокировки и журнал;
- E2EE в обе стороны, неверная фраза и конфликт версий.

Критерий: все пункты имеют фактический результат и известные ограничения занесены в issue/docs.

### 2.2. CI и публикация

- Все необходимые image matrix jobs успешно публикуют и подписывают образы.
- Устранить package Actions access/permission проблемы без широкого PAT в CI.
- Стабилизировать mobile↔keyguard integration job.
- Разобрать старые lint errors отдельно от функциональных изменений.

Критерий: повторный релиз не требует ручных обходов и исключений из проверок.

## 3. P1 — Windows distribution и повторный вход

### 3.1. Подпись и автообновление Windows

- Stable/beta и явный проверенный rollback на предыдущий stable реализованы в 0.18.1.
- Подписанный manifest, Release URL и SHA-256 проверяются перед обновлением и перед откатом.
- На реальной Windows ещё нужно проверить чистую установку, обновление и откат с сохранением device keys и пространств.
- В main electron-builder подписывает приложение и NSIS по Authenticode/SHA-256 с RFC 3161 timestamp; Release без PFX/publisher намеренно не собирается.
- CI проверяет `Valid` и точный subject обоих EXE. Клиент повторяет проверку перед update/rollback и удаляет неподписанный или чужой installer.
- Для выпуска подписанного релиза нужны `WIN_CSC_LINK`, `WIN_CSC_KEY_PASSWORD` и `DECK_WINDOWS_PUBLISHER`; реальный сертификат и Windows-приёмка ещё не подтверждены.

Критерий: опубликованные приложение и installer имеют доверенную Authenticode-подпись издателя; чистая установка, обновление и откат на подписанный stable проверены на реальной Windows; revoked device не восстанавливает доступ после update.

### 3.2. Оставшееся усиление обновлений

- Проверка доверенной Authenticode-подписи издателя Windows перед установкой реализована в main в дополнение к подписанному manifest; на опубликованном подписанном EXE ещё не проверена.
- Автоматическое обнаружение неудачного запуска и атомарный rollback; текущий ручной откат не выдаётся за эту функцию.
- Несовместимая миграция локальных данных останавливает обновление и оставляет предыдущую версию; revoked device не восстанавливает доступ.
- Для Android нужен отдельный recovery-пакет с новым `versionCode`: установка старого APK поверх нового запрещена ОС.

Критерий: на реальных Windows и Android выполнено обновление с предыдущего публичного релиза без потери состояния и повторной регистрации; после неудачного обновления работает предыдущая версия, а серверные задачи не прерываются.

## 4. P1 — автономность и синхронизация

### 4.1. Автоматическая E2EE-синхронизация

- Очередь изменений и фоновая синхронизация модулей.
- Версии/vector clock или эквивалентное обнаружение конфликтов.
- UI конфликта без молчаливого last-write-wins.
- Восстановление после смены парольной фразы и потери конверта.
- Минимизация метаданных на сервере.

Критерий: offline изменения на двух устройствах сходятся без потери; сервер видит только зашифрованный конверт и минимально необходимые метаданные.

### 4.2. Осознанное расширение backup

Отдельно решить, какие локальные настройки и данные standalone действительно нужны пользователю. Не расширять backup автоматически на все AsyncStorage, device keys или provider credentials.

## 5. P2 — второй этап Git-модулей

### 5.1. Безопасные обновления

- Diff манифеста и кода перед обновлением.
- Повторное согласование новых разрешений.
- Rollback на предыдущий pinned commit.
- Проверка совместимости с приложением.

Критерий: усиление разрешений невозможно без явного действия пользователя.

### 5.2. Git/SSH capability

- Отдельные RPC с узкой схемой, без передачи постоянных credentials модулю.
- Подтверждение write/danger через существующий action protocol.
- Лимиты времени, ответа, частоты и полный журнал.

Критерий: модуль без секрета не может обратиться к произвольному Git/SSH или выйти за allowlist.

### 5.3. Server-side sandbox

- Изолированная execution environment без нативных библиотек и произвольного Node.js по умолчанию.
- Отдельные CPU/memory/time/output quotas.
- NetworkPolicy и отсутствие доступа к keyguard secrets.
- Аттестация/подпись выпускаемых модулей и аудит запусков.

Критерий: attack tests доказывают отсутствие побега в backend/control plane/keyguard и произвольного egress.

### 5.4. Настоящий scheduler

Фоновые задания модулей реализуются только после sandbox resource limits и восстановления после перезапуска. Таймер открытой панели не выдаётся за scheduler.

Критерий каждого пункта: реальные длинные файлы, отмена, стоимость, корректный результат и отсутствие потерянных фрагментов.

## 8. P2 — эффективный agent harness, терминал и знания

### 8.1. Context/Budget Harness и скорость моделей

- Большие результаты инструментов сохраняются отдельно; модели получают только нужные строки, страницы и фрагменты. Repo map и чтение символов вместо целых репозиториев.
- Возобновление с сохранённого шага, запуск только упавших проверок и отсутствие повторной оплаты начавшегося вывода.
- Детерминированный model router по типу и сложности задачи. Обучаемый RouteLLM рассматривается только после накопления реальных метрик.
- Inspect AI для набора quality/cost/latency evals; DSPy — только офлайн-оптимизация промптов. LangGraph не заменяет текущий runtime без доказанной необходимости; второй model proxy не добавляется.

Критерий: на фиксированном наборе реальных задач снижаются стоимость и время без падения качества; cache hit, повторные чтения, остановка и возобновление измеряются отдельно для каждой модели.

### 8.2. Локальный терминал устройства для агента

- Windows: PowerShell/cmd через ConPTY, вкладки, история, фоновые процессы, остановка и ограничение вывода. Инструменты `terminal_exec`, `terminal_read`, `terminal_stop`, `terminal_jobs`.
- Режимы read-only, рабочая папка, allowlist команд и расширенный доступ; опасная команда подписывается вместе с рабочей директорией и ID устройства.
- Очищенное окружение без наследования API-ключей и токенов других программ; никакой автоматической эскалации до администратора.
- Серверный агент вызывает ПК только через защищённый device channel; offline/revoked устройство команду не выполняет.
- Android: app-private shell и виртуальная рабочая папка с ограниченными командами, без root и доступа к другим приложениям. Для серверов сохраняется SSH Gateway; системный root-терминал не обещается.
- Ручной и agent-driven терминал используют один журнал, лимиты и экран подтверждений.

Критерий: реальные команды на опубликованных клиентах, остановка/таймаут/обрыв связи, запрет неподписанной danger-команды, отсутствие секретов в env и невозможность выполнения после revoke.

### 8.3. База знаний с актуальностью и доказательствами

- Серверные embeddings добавляются только после измерения пользы FTS5/BM25, не на устройствах.
- Поиск возвращает короткие фрагменты с проектом, источником и датой проверки, а не целые заметки.
- Перед использованием особенно изменчивых сведений агент проверяет файл, commit, URL или состояние системы по требованию, а не только по расписанию.
- Evals проверяют не только поиск нужной записи, но и обнаружение устаревшего/противоречивого ответа.

Критерий: агент находит нужный фрагмент, отличает актуальную ревизию от устаревшей, показывает источник и не использует старую конфигурацию как подтверждённый факт.

## 9. Что сознательно не входит в ближайший план

- Локальные AI-модели на устройствах.
- Произвольный нативный код Git-модулей.
- Отключение device approval, DPoP, mTLS или подписи danger ради удобства.
- Экспорт/синхронизация API/GitHub-ключей в обычном backup.
- Единая кнопка «разрешить всё» вместо гранулированных правил агента.
- Полноценный root/system shell на Android без поддержки ОС.
- MCP Server Fugu Deck перенесён в бэклог без сроков: внешний доступ к возможностям Fugu Deck через MCP не проектируется и не реализуется до отдельного решения владельца, threat model и security review. Существующий MCP-клиент для подключения внешних серверов к пространству этим решением не удаляется и не меняется.

## 10. Порядок принятия следующих этапов

1. Продолжать заполнять device acceptance matrix по ошибкам реального использования.
2. Проверить stable/beta и явный Windows rollback на устройствах; выпустить и проверить Authenticode после добавления сертификата, затем автоматический rollback.
3. Продолжить Harness: repo map, durable resume, deterministic router и baseline quality/cost/latency evals.
4. Добавить короткие доказательства и on-demand проверку актуальности базы знаний.
5. Расширять PDF/OCR и media pipelines: диапазоны страниц, удалённая отмена OCR и восстанавливаемые задачи.
6. Затем перейти к автоматической E2EE-синхронизации, Windows terminal и Android app-private shell.
7. Только после этого расширять module capabilities и server execution.

Каждый этап должен иметь отдельный security review, тесты атак, обновлённую документацию и реальный сценарий на опубликованном артефакте.
