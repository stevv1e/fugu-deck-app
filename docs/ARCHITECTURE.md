# Fugu Deck: полная архитектура и требования к кластеру

*Версия от 26.09.2026. Описывает код в репозитории (коммит `42fd6b5`) и план развёртывания на Kubernetes (k3s).*

Fugu Deck — мобильное приложение (PWA) с ИИ-агентом для репозиториев GitHub и GitLab.
Многопользовательская версия работает в k3s-кластере: у каждого пользователя своё изолированное пространство,
для совместной работы создаются общие приватные пространства. Модели: Claude (Anthropic) и Sakana Fugu,
другие провайдеры подключаются адаптерами.

**Что проверено.**
- Unit-тесты.
- Сценарий «Анна / Боб / Вика» через API.
- UI-сценарий в браузере с виртуальными passkey, включая PRF.
- Одиночная (standalone) версия.
- Все 33 манифеста проходят проверку kubeconform.

**Что ещё не делалось.** Запуск с настоящими API Anthropic и Sakana и на живом кластере. Всё проверено на тестовых заглушках.

## 1. Общая схема

```
 ┌──────────── Телефоны / ноутбуки (PWA) ─────────────┐
 │  Анна            Боб             Вика               │
 │  ключи Claude/Sakana/Git — только на устройстве,     │
 │  зашифрованы ключом из passkey (PRF) или PIN         │
 └───────────────────────┬─────────────────────────────┘
                         │ HTTPS  deck.<домен>  (один адрес для всех)
                         ▼
 ┌───────────────────────── k3s-кластер (вне ЕС/UK/CH) ─────────────────────────┐
 │                                                                                │
 │  Traefik (встроен в k3s) + сертификат Let's Encrypt (cert-manager)             │
 │     │  /  и  /cp/api/*                    │  /s/<id>/*                          │
 │     ▼                                     ▼                                     │
 │  ns deck-system                        ns deck-u-…  deck-u-…  deck-t-…          │
 │  ┌───────────────────────┐   создаёт   ┌──────────┐┌──────────┐┌──────────┐    │
 │  │ control-plane          │ ─────────▶ │ личное   ││ личное   ││ общее    │    │
 │  │ • PWA (статика)        │  Kubernetes │ простр.  ││ простр.  ││ простр.  │    │
 │  │ • passkey, ники        │     API     │ FastAPI  ││ FastAPI  ││ FastAPI  │    │
 │  │ • токены ES256         │             │ SQLite   ││ SQLite   ││ SQLite   │    │
 │  │ • приглашения, роли    │ ──roster──▶ │ PVC 2 ГБ ││ PVC 2 ГБ ││ PVC 2 ГБ │    │
 │  │ • уборщик 48/72 ч      │ ──revoke──▶ └────┬─────┘└────┬─────┘└────┬─────┘    │
 │  │ SQLite, PVC 1 ГБ       │                  └───────────┼───────────┘          │
 │  └───────────────────────┘                              ▼ :3128                 │
 │                                   ns deck-egress: tinyproxy (белый список)      │
 │  ns argocd: Argo CD ◀── git (GitOps)                    │                       │
 └─────────────────────────────────────────────────────────┼───────────────────────┘
                                                           ▼
                      api.anthropic.com · api.sakana.ai · api.github.com · gitlab.com
```

**Главные принципы.**
1. **Ключи ИИ и Git не хранятся на сервере.** Они лежат зашифрованными на устройстве. В под пространства ключи попадают только в оперативную память: пока идёт работа, и ещё 30 минут после.
2. **Изоляция по пространствам.** Отдельный namespace, диск, NetworkPolicy и квота на каждое пространство.
3. **Сервер знает минимум о людях.** control-plane хранит ники, публичные ключи passkey, членство и время последнего входа. Чатов, памяти и ключей в нём нет.
4. **72 часа без входа — данные удаляются.** Через 48 ч приходит предупреждение, через 72 ч данные удаляются.
5. **Состояние кластера описано в git (GitOps).** Пространства — это данные, а не конфигурация, поэтому их создаёт control-plane, а не git.

## 3. Клиент (PWA)

- **Стек.** React 19, Vite 7, TypeScript, vite-plugin-pwa (офлайн-оболочка, установка на главный экран). Темы задаются CSS-переменными через `data-theme`.
- **Режим работы** определяется через `/cp/api/info`. Если control-plane отвечает, это кластер. Если нет — одиночная версия с паролем.
- **Хранилище ключей** (`vault.ts`):
  - ключи Claude, Sakana, GitHub и GitLab шифруются AES-GCM;
  - ключ шифрования выводится из WebAuthn PRF (секрет passkey, HKDF) или, если PRF нет, из PIN (PBKDF2-SHA256, 600 000 итераций);
  - результат PRF **никогда не уходит на сервер**: из ответа WebAuthn он вырезается до отправки.
- **Работа с пространством.**
  - Приложение получает у control-plane токен пространства (10 мин) и обновляет его заранее.
  - После разблокировки хранилища ключи отправляются в `POST /s/<id>/api/session/keys`.
- **Потоки событий (SSE).**
  - `/cp/api/events`: приглашения, уведомления, изменения состава.
  - Поток открытого пространства: присутствие, изменения чатов, события запуска агента.
  - После обрыва связи поток запуска дочитывается с того же места (`after=N`).
- **Экраны.** Чат, память, скилы, проект, пространство (участники, приглашения, расходы), настройки (ключи, темы, коды приглашений для админа).

## 4. control-plane

**Стек.** FastAPI, aiosqlite, py_webauthn, PyJWT (ES256/HS256), клиент kubernetes. Один под, стратегия `Recreate` (SQLite).

### 4.1. Вход и токены

| Что | Как |
|---|---|
| Регистрация | одноразовый код приглашения (первый — `CP_BOOTSTRAP_CODE`) → ник → passkey |
| Вход | passkey (Face ID / отпечаток); паролей нет |
| Сессия | cookie `HttpOnly`, `Secure`, HS256, 7 дней |
| Токен пространства | ES256 JWT, 10 мин: `sub`, ник, `aud=space:<id>`, роль (owner / editor / viewer), `jti` |
| Служебные токены | ES256, `aud=space-internal:<id>`: `revoke` (отзыв участника), `roster` (состав для голосований) |

Пространство проверяет подпись публичным ключом из ConfigMap `space-config`. Заголовкам клиента оно не доверяет.

### 4.2. API (29 маршрутов, группы)

- **Вход.**
  - `/cp/api/info`, `/cp/api/health`;
  - регистрация и вход по passkey (begin / finish), выход, `me`;
  - `/cp/api/test/login` — только при `CP_TEST_MODE=true`, в проде выключен.
- **Пространства.** Список, создание общего, «сделать общим», выдача токена.
- **Люди.**
  - Приглашения: по нику из выпадающего списка; принять или отклонить.
  - Участники: смена роли, удаление.
- **Админ.** Коды приглашений, список пользователей, ручной запуск уборщика.
- **События.** SSE `/cp/api/events`, уведомления.
- **Статика.** SPA; в режиме local ещё прокси `/s/<id>/…` (для разработки).

### 4.3. Оркестратор пространств

Режим `kubernetes` (прод) через server-side apply создаёт для каждого пространства:

`Namespace` (PSS **restricted**) → `ResourceQuota` → `ConfigMap` (публичный ключ) → `PVC` → `Deployment` (1 реплика, `Recreate`)
→ `Service` → `NetworkPolicy` → Traefik `Middleware` (stripPrefix) → `IngressRoute` (`/s/<id>/`).

При старте control-plane обновляет все пространства до текущего образа.
Режим `local` запускает пространства процессами; он нужен для разработки и тестов.

### 4.4. Уборщик 48/72 ч

Фоновая задача внутри control-plane, раз в час (`CP_REAPER_INTERVAL`).

- **48 ч без входа.** Пользователь получает уведомление.
- **72 ч без входа.** Действия:
  - удаляется личное пространство вместе с namespace, подом, диском, чатами и памятью;
  - если пользователь был владельцем общего пространства, владение передаётся другому участнику;
  - если участников в общем пространстве не осталось, оно удаляется целиком;
  - пользователь исключается из остальных общих пространств: его токены отзываются, поток событий закрывается, список голосующих обновляется.
- **Повторный вход.** Пользователь получает пустое пространство. Ключи остались на телефоне, вводить их заново не нужно.

## 5. Пространство (Fugu Deck)

**Стек.** FastAPI, aiosqlite (миграции v1–v6, FTS5 для поиска по памяти), httpx, anthropic SDK. 52 маршрута API.

### 5.1. Агент

- **Цикл.** Модель → вызовы инструментов → результат → модель. Не больше `MAX_AGENT_STEPS=30` шагов.
- **Журнал запуска.** Все события пишутся в журнал с номерами. Клиент может переподключиться и дочитать события с нужного номера.
- **Провайдеры** (`LLMProvider`):
  - `AnthropicProvider`: Messages API, стриминг, tool use, кэширование промпта, thinking-блоки с подписью возвращаются в модель без изменений;
  - `OpenAICompatProvider`: Sakana Fugu, позже OpenAI и xAI.
- **Модель задаётся как `provider:model`.** Цены берутся из `PRICING_JSON`.

| Модель | Цена за 1M токенов (вход / выход) |
|---|---|
| `anthropic:claude-sonnet-5` | $2 / $10 |
| `anthropic:claude-opus-5-5` | $4 / $20 |
| `anthropic:claude-haiku-4-5` | $1 / $5 |
| `sakana:fugu-max-v1.0` | $2 / $6 |
| `sakana:fugu-ultra-v2.0` | $5 / $30 |

- **Инструменты и риск.**
  - Чтение: `list_repos`, `repo_info`, `list_files`, `read_file`, `ci_status`, вложения, память, скилы — выполняются без подтверждения.
  - Запись: `create_repo`, `create_branch`, `create_pull_request`, `commit_files` в рабочую ветку — нужно подтверждение.
  - Опасные: `commit_files` в ветку по умолчанию — карточка DANGER.
  - Подтвердить может редактор или владелец. Все действия пишутся в `audit_log`.
- **Git** работает через REST API GitHub и GitLab. Клонов на диске нет, поэтому диск пространства почти не растёт.

### 5.2. Проекты, память, скилы

- **Проект** — это чаты, инструкции, участники и память.
- **Память.**
  - Агент записывает её сам, пользователь правит вручную.
  - Поиск по памяти — FTS5.
  - Доступ к памяти другого проекта **только на чтение** (`memory_links`).
- **Скилы** лежат в папке `skills/<имя>/SKILL.md` с frontmatter. Агент загружает их инструментом `load_skill`.
- **Экспорт и импорт проекта.** «Сделать общим» копирует память, инструкции и скилы в общее пространство.

### 5.3. Realtime

- Брокер SSE в процессе рассылает события: присутствие (кто и с каких устройств), изменения чатов, события запусков.
- Несколько агентов в одном проекте могут работать параллельно, все участники видят их в реальном времени.
- Удалённого участника отключают командой `kick`.

### 5.4. Модель общего чата

- **Модель и оплата.**
  - В общем чате работает **одна модель**. Её оплачивает **спонсор** своим ключом (ключ в RAM, пока спонсор в сети, плюс 30 мин).
  - **Лимит спонсорства обязателен:** сумма в $ или в токенах (пересчитывается в $ по цене модели) **и/или** дата окончания в календаре (действует до конца дня по `DISPLAY_TZ`, по умолчанию Europe/Moscow).
  - Когда лимит исчерпан или срок истёк, агент останавливается. Спонсор может поднять лимит или перестать оплачивать.
- **Правило смены модели** выбирается при создании чата. Позже его может поменять создатель чата или владелец.
  - **По голосованию** (по умолчанию). Голосуют редакторы и владельцы.
    - Модель меняется, когда «за» проголосовало большинство.
    - Если большинство уже недостижимо, предложение отклоняется.
    - **Таймер 24 ч** (`PROPOSAL_TTL_SECONDS`): после него предложение закрывается с отметкой «истекло».
  - **Разрешена коллегам.** Любой редактор меняет модель сразу и становится спонсором.
- **Отметки в ленте:** кто выбрал модель, кто голосовал, кто платит.
- **Расходы.** В каждой записи расходов хранится, кто запустил запрос и чей ключ платил. Сводка по участникам: сегодня, 7 дней, 30 дней, всё время, с разбивкой по моделям.

## 6. Хранение ключей и секретов

| Что | Где | Защита |
|---|---|---|
| Пароль | нигде | вход только по passkey |
| Passkey | чип устройства | на сервере только публичный ключ |
| Ключи ИИ и Git | IndexedDB устройства | AES-GCM; ключ шифрования — из PRF passkey (HKDF) или из PIN (PBKDF2, 600k итераций) |
| Ключи в работе | RAM пода пространства (`KeyVault`) | TTL 30 мин после последней активности; не пишутся на диск и в логи; не видны другим участникам |
| Ключ подписи токенов | PVC control-plane (`space-signing.pem`) | доступен только поду control-plane; **обязательно в бэкап** |
| Секрет сессий | PVC control-plane (`session.secret`) | то же |
| `CP_BOOTSTRAP_CODE` | Secret `control-plane-secrets` | в git не хранится; etcd зашифрован (`--secrets-encryption`) |
| Токен пространства | память приложения | 10 мин, привязан к пространству и роли, отзывается |

## 7. Основные потоки

**Вход и открытие пространства**
```
PWA → passkey → control-plane: cookie сессии (7 дн.)
PWA → POST /cp/api/spaces/<id>/token → JWT ES256 (10 мин, роль)
PWA → Traefik /s/<id>/api/... (Bearer) → stripPrefix → Service space → проверка подписи и отзыва
PWA → разблокировка ключей (PRF/PIN) → POST /s/<id>/api/session/keys → RAM пода
```

**Запуск агента**
```
сообщение → run → провайдер (ключом запустившего или спонсора) через egress-прокси
         → инструменты (GitHub/GitLab через прокси) → карточки подтверждения
         → события SSE всем участникам → учёт: user_id, payer_id, токены, $
```

**Общий проект**
```
«＋ общий проект» → ник из списка → роль → приглашение (SSE) → «Принять»
control-plane → namespace deck-t-… → roster → пространство
```

**Удаление участника или уборка по 72 ч**
```
control-plane → /internal/revoke (служебный токен) → токены отклоняются, SSE закрыт
             → /internal/roster → пересчёт голосующих
```

## 8. Сеть и изоляция

- **Вход в пространство** разрешён только от Traefik (kube-system) и control-plane (deck-system), порт 8000.
- **Выход из пространства** разрешён только в DNS (kube-dns :53) и к egress-прокси (:3128). Прямого интернета нет, соседей по кластеру не видно.
- **Egress-прокси** (tinyproxy) работает по правилу «запрещено всё, кроме списка»:
  - `api.anthropic.com`, `api.sakana.ai`, `api.openai.com`, `api.x.ai`;
  - `api.github.com`, `github.com`, `gitlab.com`;
  - только порт 443. Свой GitLab добавляется в `allow.txt`.
- **control-plane** принимает трафик только от Traefik.
- **Поды:**
  - `runAsNonRoot`, UID 10001;
  - `readOnlyRootFilesystem`, `drop ALL`, seccomp `RuntimeDefault`;
  - без токена ServiceAccount (у пространств);
  - namespace с PSS `restricted`.
- **RBAC control-plane:** только namespaces, quotas, configmaps, PVC, services, deployments, networkpolicies, IngressRoute/Middleware.
- **HTTP-заголовки:**
  - HSTS, CSP (`default-src 'self'`), `frame-deny`, `no-referrer`;
  - Permissions-Policy без камеры, микрофона и геолокации.

## 9. Что лежит в git и что создаётся на лету

| Namespace | Кем создаётся | Содержимое |
|---|---|---|
| `kube-system` | k3s | Traefik, CoreDNS, local-path-provisioner, metrics-server |
| `argocd` | вручную (1 раз) | Argo CD |
| `cert-manager` | Argo CD (Helm-чарт jetstack v1.16.2) | cert-manager + ClusterIssuer Let's Encrypt |
| `deck-egress` | Argo CD (`infra/platform`) | tinyproxy |
| `deck-system` | Argo CD (`infra/control-plane/overlays/prod`, kustomize) | control-plane, PVC 1 ГБ, сертификат, маршруты, RBAC |
| `deck-u-<id>` / `deck-t-<id>` | **control-plane** | пространства пользователей и команд |

**Структура репозитория**

```
backend/          пространство (FastAPI) + тесты и заглушки
control-plane/    control-plane (FastAPI) + e2e «три пользователя»
frontend/         PWA
infra/bootstrap/  root-app Argo CD (app-of-apps)
infra/apps/       cert-manager, platform, control-plane
infra/platform/   ClusterIssuer, egress-прокси
infra/control-plane/base + overlays/prod
deploy/           docker-compose для одиночной версии
.github/workflows, .gitlab-ci.yml
```

**Цикл обновления.** `git push` → CI: тесты → образы в GHCR → коммит `deploy: <sha>` с новым тегом → Argo CD выкатывает control-plane.
control-plane при старте обновляет пространства до нового образа.

## 10. Требования к ресурсам

### 10.1. Что измерено

Замеры сделаны на тестовом сценарии «три пользователя» (заглушки вместо API провайдеров). Резидентная память процессов (RSS):

| Процесс | Покой | Пик в сценарии |
|---|---|---|
| control-plane | ~70 МБ | **~80 МБ** |
| пространство | ~70 МБ | **~110–125 МБ** (агент, SSE, несколько участников) |
| данные пространства на диске | ~0,5 МБ новое | ~1,5 МБ общее после сценария |

С настоящими провайдерами (длинные ответы, большие файлы, вложения до 25 МБ) закладываем **150–250 МБ** на активное пространство.
Агент почти всё время ждёт ответа модели, поэтому процессор нагружается только короткими всплесками (JSON, SSE, TLS).

### 10.4. Сколько нужно

Число пространств ≈ число пользователей + общие проекты (примерно половина от числа людей).
Формула памяти: **RAM ≈ (2,5 ГБ + 0,2 ГБ × пространств) × 1,5 запаса**.

| Пользователей | Пространств | vCPU | RAM | Диск (SSD/NVMe) | Схема |
|---|---|---|---|---|---|
| **5 (минимум)** | ~8 | 2 | 4 ГБ | 40 ГБ | 1 нода, без мониторинга, впритык |
| **5 (рекомендуется)** | ~8 | **4** | **8 ГБ** | **80 ГБ** | 1 нода, лёгкий мониторинг, запас под обновления |
| 15 | ~22 | 4–6 | 16 ГБ | 120 ГБ | 1 нода |
| 30 | ~45 | 8 | 24–32 ГБ | 200 ГБ | 1 большая нода или 2 ноды (см. 10.7) |
| 50+ | 75+ | 12+ | 48 ГБ+ | 300 ГБ+ | 3 ноды, общее хранилище, усыпление неактивных пространств |

**Расчёт для 5 человек (8 пространств):**
- в обычной работе: ~2,3 ГБ система + 8 × 0,15 ГБ = **~3,5 ГБ**;
- в худшем случае, если все пространства упрутся в лимит 512Mi: ~2,3 + 8 × 0,5 = **~6,3 ГБ**;
- поэтому рекомендуется 8 ГБ;
- на 4 ГБ всё запустится, но одновременная тяжёлая работа всех участников и обновление Argo CD могут упереться в память.

### 10.5. Диск

| Что | Объём |
|---|---|
| ОС | 8–10 ГБ |
| Образы контейнеров: k3s ~1 ГБ, Argo CD ~1,5 ГБ, cert-manager ~0,2 ГБ, space и cp по ~0,3 ГБ, плюс старые версии до сборки мусора kubelet | 5–8 ГБ |
| PVC: 8 × 2 ГБ + 1 ГБ | 17 ГБ (для 5 человек) |
| Логи (ограничьте journald до 1–2 ГБ) | 2–5 ГБ |
| Локальные копии бэкапов (если без S3) | 5–10 ГБ |

> **Важно.** Хранилище `local-path` в k3s **не ограничивает** реальный размер PVC: 2 ГБ — только заявка, и одно пространство может занять весь диск.
> Защита сейчас: вложения до 25 МБ (`MAX_UPLOAD_MB`), репозитории не клонируются.
> Для надёжности: отдельный раздел под `/var/lib/rancher/k3s/storage`, мониторинг свободного места (оповещение при 80 %), либо XFS project quotas или Longhorn.

### 10.6. Сеть, домен, доступы

- **Сервер вне ЕС, Великобритании и Швейцарии.** Это требование Sakana к использованию Fugu.
  Доступность Claude определяется тем, где находятся сами пользователи, а не тем, где стоит сервер.
- **Публичный IPv4**, A-запись `deck.<домен>` → IP. Нужен только один хост: пространства отдаются по путям `/s/<id>/`, wildcard-сертификат не нужен.
- **Входящие порты:**
  - 80 и 443 открыты всем (Let's Encrypt HTTP-01 и приложение);
  - 22 и 6443 — только с вашего IP или через WireGuard/SSH-туннель.
- **Исходящие с ноды:**
  - HTTPS к провайдерам ИИ и Git (через egress-прокси);
  - `ghcr.io`, `github.com` (Argo CD и образы);
  - `quay.io`, `docker.io`, `charts.jetstack.io` (cert-manager, tinyproxy);
  - `acme-v02.api.letsencrypt.org`.
- **Канал:** 100 Мбит/с с запасом. Трафик на 5 человек — единицы ГБ в месяц, в основном загрузка образов при обновлениях.

### 10.7. Одна нода или несколько

- **Сейчас (этап 1) всё рассчитано на одну ноду.** Пространства и control-plane используют SQLite, поэтому у каждого одна реплика. Тома `local-path` привязаны к ноде: если она упадёт, её пространства недоступны до восстановления.
- **Две ноды и больше.** Манифесты менять не нужно: новые пространства просто распределятся по нодам. Но каждое пространство остаётся на ноде, где лежит его диск.
- **Отказоустойчивость** (переезд пространства при падении ноды) требует:
  - 3 нод;
  - распределённого хранилища Longhorn (+~0,5–1 ГБ RAM на ноду, реплика ×2–3 на диске);
  - встроенного etcd k3s в HA-режиме;
  - перевода control-plane на Postgres (CloudNativePG).
- **Лимит плотности:** 110 подов на ноду (по умолчанию k3s). Это ~90 пространств, но упрётесь вы раньше в память.

### 10.8. Рекомендуемая конфигурация для старта

- **1 VPS:** 4 vCPU, 8 ГБ RAM, 80 ГБ NVMe, Ubuntu 24.04, публичный IPv4, вне ЕС/UK/CH.
- **k3s** последней стабильной версии с `--secrets-encryption`. Traefik, local-path и NetworkPolicy уже встроены.
- **Argo CD:** выключить dex и notifications (экономия ~150 МБ).
- **Мониторинг:** VictoriaMetrics single + Grafana. Оповещения: диск > 80 %, память ноды > 85 %, под в `CrashLoopBackOff`, сертификат истекает < 14 дней.
- **Бэкап:** ежедневно, `sqlite3 .backup` по PVC → restic → S3-хранилище вне ЕС.
  - **control-plane — обязательно.** Без его базы и ключа подписи всем придётся регистрироваться заново.
  - **Пространства хранить не дольше 72 ч**, иначе нарушится обещание удалить данные.

## 12. Чек-лист перед продом

1. Сервер вне ЕС/UK/CH. Открыты только 80/443, SSH и 6443 — с вашего IP.
2. k3s с `--secrets-encryption`. Argo CD установлен, в `infra/` подставлены домен и логин GHCR.
3. Создан `control-plane-secrets` с `CP_BOOTSTRAP_CODE`. **`CP_TEST_MODE` не задан (false).**
4. Закреплены digest образов tinyproxy и своих образов (CI ставит тег по sha).
5. Сертификат выпущен, `https://deck.<домен>` открывается, первый вход по коду.
6. Настроены бэкап control-plane и мониторинг диска и памяти.
7. Первый запуск с настоящими ключами Anthropic и Sakana на тестовом проекте.
