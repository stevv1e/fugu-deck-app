# Техническая архитектура Fugu Deck

Документ описывает логическую архитектуру приложения 0.11.0 и серверных компонентов 0.11.x. Конкретные адреса, секреты и параметры приватного кластера в публичную документацию не входят.

## 1. Компоненты

```text
┌────────────────────── Клиенты ──────────────────────┐
│ Android: React Native / Expo / fd-secure            │
│ Windows: общий Expo web bundle / Electron / Node net │
└───────────────────────┬─────────────────────────────┘
                        │ HTTPS, OAuth, DPoP; затем mTLS
┌───────────────────────▼─────────────────────────────┐
│ Edge / Traefik                                      │
│ invite-gate, rate limit, mTLS, доверенные заголовки │
└──────────────┬──────────────────────┬───────────────┘
               │                      │
┌──────────────▼───────────┐  ┌───────▼────────────────┐
│ Control Plane            │  │ Keycloak               │
│ invites, pairing, spaces │  │ passkey, OAuth/OIDC    │

               │                      │
```

### Клиенты

- `mobile/` — общий интерфейс Expo Router и React Native. На Android нативный `fd-secure` работает с StrongBox/TEE и аттестацией.
- `desktop/windows/` — Electron shell, защищённая схема `fugu-app://`, preload bridge, Node HTTP(S) transport с поддержкой mTLS, deep links `fugudeck://`. File bridge открывает нативные picker/save dialogs, принимает реальные dropped Files через `webUtils`, читает/пишет частями и выдаёт renderer только случайные handles выбранных файлов, а не произвольный доступ к путям. Update bridge проверяет Ed25519-manifest и SHA-256, сохраняет только проверенный installer handle и запускает его по действию пользователя.
- `local/` — standalone-клиент без кластерного backend.

### Space backend

FastAPI отвечает за чаты, проекты, агентов, инструменты, базу знаний, расписания, медиа-задачи, отчёты и Drive-интеграцию. В кластере вызовы внешних AI/Git/MCP/web API направляются через keyguard. Один backend-процесс хранит часть активного runtime-состояния; долговременные пользовательские данные должны рассматриваться отдельно от памяти процесса.

Agent Harness использует стабильный cached prefix, отдельный снимок памяти, compaction истории и сокращение старых tool results. Запуск ограничивается шагами, временем, суммарными токенами, стоимостью и числом tool calls; последовательные read-only вызовы выполняются параллельно, а write/dangerous остаются последовательными.

### Control Plane

Публичный API кластера: приглашения, пользователи, pairing, устройства, личные и общие пространства, роли, Drive OAuth и служебные маршруты. Подписи действий не подменяются control plane: криптографическую проверку выполняет keyguard.

### PDF/OCR worker

`app.media_worker` дополнительно принимает PDF до 200 МБ/400 страниц. PyMuPDF извлекает текст, таблицы и метаданные изображений; Tesseract OCR запускается только при отсутствии текстового слоя. `process_pdf` может ограничить диапазон `start/end`, создаёт Markdown/JSON и хранит параметры в SQLite. В кластере запрос идёт `space → keyguard /media/pdf → Malaysia worker`; фиксированные `status/result/cancel` позволяют продолжить опрос и остановить активный OCR. Keyguard сам подставляет namespace пространства, worker не принимает чужую задачу по одному угадыванию ID. NetworkPolicy запрещает worker произвольный egress, активное содержимое PDF не исполняется. Статус/результат worker находятся в памяти ограниченное время; параметры Space и checkpoints завершённых аудиофрагментов — в SQLite schema v30 без секретов.

### Keyguard

Единственный компонент, который должен читать секреты провайдеров из защищённого хранилища и подставлять их в исходящие запросы. Он также:

- ведёт реестр устройств и их состояния pending/active/revoked;
- проверяет JWS-действия, сроки и одноразовые nonce;
- проверяет DPoP и соответствие ключа токена/сертификата;
- контролирует allowlist внешних вызовов, цены и лимиты;
- выпускает/запрашивает сертификаты устройств через OpenBao PKI;
- фильтрует ответы и не возвращает секреты агенту.

## 2. Идентичность устройства

При регистрации создаются два независимых P-256 ключа:

- **session key** — DPoP, CSR и последующий mTLS;
- **confirmation key** — подписи пользовательских действий.

`device_id` выводится из thumbprint confirmation key. CSR подписывается session key, а `device_enroll` связывает оба thumbprint. Keyguard проверяет структуру, подписи, сроки и повторное использование nonce.

На Android ключи могут находиться в StrongBox/TEE и иметь аттестацию. Windows использует программное защищённое хранилище клиента; pairing не выдаёт ему аппаратную аттестацию.

## 3. Мобильный OAuth/passkey flow

```text
Invite → join/start → Keycloak passkey → authorization code
→ PKCE exchange + DPoP → access/refresh tokens
→ enroll request + session DPoP + signed device_enroll + CSR
→ keyguard creates pending device → device_approve → certificate
```

Проверки:

- приглашение одноразовое и привязано к нику;
- `state` и PKCE защищают возврат OAuth;
- токен обязан иметь тип DPoP и правильный `cnf.jkt`;
- refresh также требует DPoP ключом устройства;
- новое устройство остаётся pending до отдельной подписи владельца/администратора.

## 4. Windows pairing без Bluetooth/USB

### 4.1. Создание

Windows сначала создаёт session/confirmation keys и получает обычный enrollment challenge. Затем вызывает:

`POST /v1/pair/start` с приглашением, именем ПК и двумя публичными thumbprint.

Control plane создаёт:

- pairing ID — 32 случайных байта;
- pairing secret — 32 случайных байта, в базе только SHA-256;
- человекочитаемый код — 8 символов из 32-символьного алфавита;
- срок — не более 15 минут и не дольше приглашения;
- запись с ником, именем, session/confirmation JKT и device ID.

Секрет попадает в HttpOnly pairing cookie через `/start`. Приглашение на этом шаге не расходуется.

### 4.2. Подтверждение телефоном

Телефон вызывает `/v1/pair/lookup` по коду через активную mTLS/DPoP-сессию. Перед подписью приложение показывает ник, имя ПК, код и device ID.

Подписывается `pair_approve` с полями:

```text
pairing, user, target, name, code, session_jkt
+ device_id подписавшего, nonce, timestamp
```

Keyguard проверяет confirmation key активного устройства, срок, nonce и право подтверждать пользователя. Control plane сравнивает все поля с исходной записью и атомарно отмечает pairing approved. Повторное подтверждение отклоняется.

### 4.3. OAuth после подтверждения

Браузер ПК периодически обновляет страницу. При каждом запросе Traefik вызывает control plane invite-gate и перезаписывает доверенные заголовки:

- `X-Deck-Invite-Nick`;
- `X-Deck-Pair-Status`: none/pending/approved/invalid.

Keycloak показывает ожидание при pending. При approved его authenticator завершает обычный authorization code flow. Приложение дальше использует тот же PKCE/DPoP/enroll путь, что мобильный клиент.

Pairing не активирует устройство: после enroll требуется обычный `device_approve`. Мобильный passkey flow при отсутствии pairing cookie не меняется; обычный `/start` стирает старую pairing cookie.

## 5. Подписанные действия

Действие — компактный JWS ES256 над каноническим JSON. Конверт содержит тип, строго определённые поля, device ID, nonce и timestamp; действия пространства дополнительно содержат space.

Примеры: `device_enroll`, `device_approve`, `pair_approve`, `invite_create`, `key_put`, `agent_rights`, `ssh_write`, `ssh_danger`, `tool_approve`.

Схема приложения и keyguard должна совпадать. Лишние поля, управляющие/невидимые символы, неправильный тип, старый timestamp и повтор nonce отклоняются. Текст биометрии строится из тех же проверенных полей, которые подписываются.

Общие детерминированные векторы: `mobile/tests/vectors.ts` → `fugu-deck-keyguard/testdata/action-vectors.json` в приватной монорепе.

## 6. Доступ к API после активации

Обычный запрос к API требует согласованную комбинацию:

1. mTLS-сертификат устройства;
2. DPoP access token Keycloak с `cnf.jkt`;
3. отдельное DPoP-доказательство на метод/URL запроса;
4. активный, неотозванный статус устройства.

Отзыв устройства прекращает доступ независимо от оставшегося срока сертификата. Space backend дополнительно получает краткоживущий служебный токен и роль пользователя.

## 7. Модели и секреты

Ключ API шифруется на устройстве с HPKE для публичного ключа keyguard. Подписанное действие включает hint и хэш шифротекста, но не секрет. Keyguard расшифровывает и сохраняет ключ в защищённом хранилище.

Вызов модели проходит через provider-specific proxy: разрешённые поля и пути, цена, резерв/фактический расход, потоковый ответ и фильтрация секретов. Добавление модели без server-side proxy, цены и лимита не считается завершённым.

## 8. Media и Drive

Media Core отвечает за большие загрузки, разбиение, FFmpeg, фоновые задачи, прогресс и отмену. Медиафайлы до 2 ГБ загружаются частями. В кластере видео потоком проходит через keyguard в выделенный FFmpeg-воркер, который возвращает только проверенный tar-архив аудиофрагментов OGG; исходное видео провайдеру транскрибации не отправляется. Провайдер транскрибации вызывается через keyguard. Длинные ответы модели проверяются на формат и восстанавливаются по частям.

Google Drive использует OAuth authorization code + PKCE, state и offline refresh token. Keyguard получает refresh token через защищённый exchange и выполняет ограниченные Drive-запросы. Операции включают чтение, загрузку и создание папок.

## 9. Git-модули

Модуль состоит из `module.json` и JavaScript, привязанных к commit и SHA-256. Официальный индекс загружается по commit и проверяется Ed25519 по сырым байтам файла.

Sandbox ограничивает выполнение WebView/iframe и RPC. В текущей версии разрешены ограниченное storage и сеть по allowlist. Секреты приложения модулю напрямую не выдаются. Пользовательские источники не получают доверие официальной подписи.

E2EE-перенос использует PBKDF2-SHA256 (200 000 итераций) и XChaCha20-Poly1305. Экспортируются только модули/манифесты/код. Ручная синхронизация использует серверный зашифрованный конверт с optimistic conflict detection.

## 10. Границы безопасности

- Компрометация control plane не должна позволить подделать confirmation key или активировать устройство.
- Компрометация Space backend не должна раскрыть исходные API-ключи или разрешить произвольный egress.
- Pairing заменяет только браузерную аутентификацию Windows, но не вторую активацию устройства.
- Пользовательские модули не являются доверенным нативным кодом.
- Git/SSH и server-side module execution сознательно не включены в текущую модель безопасности.
- Публичная документация не должна содержать refresh tokens, пароли, приватные ключи, PAT, реальные pairing secrets или закрытые параметры кластера.

## 11. Основные ограничения текущей версии

- Windows installer пока без подписи издателя и автообновления.
- E2EE-синхронизация модулей ручная, а не фоновая.
- Модульное расписание не является системным фоновым scheduler.
- Локальные AI-модели не запускаются.
- Общая история чатов синхронизируется серверным пространством, а не E2EE module backup.
